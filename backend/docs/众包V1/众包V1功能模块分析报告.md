# 众包 V1 功能模块分析报告

> 审阅日期：2026-07-19
>
> 审阅范围：`docs/众包V1/` 下 10 份 DOCX、8 份 XLSX，以及本仓库现有任务、权限、多租户、材料摄入、证据链、订正、回款和路由实现。
>
> 报告性质：需求与架构评审，不代表法律意见；合同、个人信息、用工关系、支付税务和现场调查边界必须由正式法务复核。

## 1. 执行摘要

### 1.1 总体结论

当前材料已经能够说明众包业务的目标、角色、任务类型、质控关系和主要激励方式，适合继续做业务评审；但它还不是一套可以直接建表、开发接口并上线结算的实施规格。

**建议结论：暂不直接进入编码和数据库设计。先完成 P0 规则定版与法务审查，再形成 V1.1 权威规则基线和技术设计。**

主要原因不是功能数量多，而是四条核心链路尚未闭合：

1. **权利链未闭合**：先到先得只描述了时间戳，没有定义查重主键、原子确权、修订、撤回、并发冲突、异议和幂等。
2. **资金链未闭合**：净回款、成本扣减、多人贡献、AI 发现、S 级建言、撤销和冲正没有形成可复算的分录规则。
3. **证据链未闭合**：资产表只有“数据值 + 数据来源”，缺少文件、页码、照片、采集人、时间、位置、哈希、审核版本等证据锚点。
4. **权限链未闭合**：全员匿名、资深专家可读全部资料、敏感全文授权、众包人员仅看自己提交等规则之间缺少明确优先级，现有报告段权限也无法替代投稿对象级权限。

### 1.2 推荐的系统边界

众包应被视为一个**独立的事务型业务域**，而不是直接新增为 LangGraph 节点。任务抢单、投稿、确权、复核、审定、结算、申诉和清退必须由数据库事务、确定性 API、持久化任务队列和不可变台账保证；LLM 只适合参与分类、字段提取、相似度查重建议、风险提示和报告重算。

推荐的数据流是：

```text
众包任务发布
  -> 接单/投稿/证据上传
  -> 确定性查重与确权
  -> C 初调 / B 复核 / A 审定
  -> 审核通过形成标准 claim/material
  -> 投影到 AI Hunter 摄入、证据链和报告重算
  -> 贡献归因与结算台账
```

任何未审核投稿都不应直接写入权威订正、知识图谱有效 claim 或正式报告。

## 3. 业务边界判断

### 3.1 这不是“给现有任务表加几个状态”

众包 V1 实际包含至少九个子域：

1. 身份、实名与合规准入
2. 任务市场、匹配、接单与释放
3. 投稿、结构化表单与证据采集
4. 查重、先到先得与权益确权
5. C 初调、B 复核、A 审定质控
6. 计价、贡献归因、奖励与结算台账
7. 伯乐引荐关系和质控责任
8. 争议、处罚、清退与注销
9. 审核通过数据向 AI Hunter 的投影

现有 `task_api` 仅提供批量创建和通用任务管理，适合 SOP 督办，不具备众包所需的抢单、确权、盲测、质控、结算和争议语义。将这些行为挤进现有任务状态会造成权限、审计和资金口径混乱。

### 3.2 “伯乐”是质控链，不应继续按多级分销理解

本版《伯乐引荐与质控制度》已明确：C 完成初调，B 实际复核，A 实际审定，三笔费用分别对应独立工作，不按下级人数或业绩抽成。因此，本版核心是**引荐关系叠加质量责任链**，不是旧材料中的三级/四级分销。

仓库现有 `docs/plans/业务框架与设计稿对照及缺口.md` 仍把伯乐描述为三级/四级分销，属于旧版结论。待业务确认众包 V1 为新权威版本后，应同步标记旧结论失效，避免后续按错误模型建计酬引擎。

## 4. P0：进入实施前必须解决

### 4.1 合同主体和制度权威版本不统一

材料中出现以下主体或品牌：

- 特资第零（成都）数字科技有限公司
- 安诺数字科技有限公司
- 安诺特信云科技有限公司
- 安诺特信 / 安诺特信众包平台

保密协议标题为“021保密协议”，众包服务协议标题为“AN-ZD-021众包服务协议”，编号也可能冲突。若这些名称分别代表运营方、签约方、数据处理者和平台品牌，应在总则和各协议中明确关系；若不是，应统一主体、统一编号体系、统一版本号和生效日期。

**建议门禁**：建立一份“文件目录与效力层级表”，包含文件编码、版本、签约主体、适用岗位、上位文件、冲突裁决顺序、生效/废止日期和责任部门。

### 4.2 承揽关系表述与实际管理强度冲突

《众包服务协议》称平台只验收成果、不管理工作过程；其他制度同时规定 6 小时自然时长响应、阅读/任务数量要求、暂停权限、清退和持续质控责任。仅在合同中声明“非劳动关系”不能消除实际管理行为带来的重新认定风险。

**建议**：由法务从实际运营动作反推合同，不只修改措辞。至少明确：是否自由接单、是否可拒单、工作地点和工具是否自备、是否允许替代履行、是否排他、是否有最低工作量、超时后果、质控是成果验收还是过程管理。

### 4.3 个人信息与知识产权条款过宽

高风险条款包括：

- 平台可对上传的信息、数据和资料进行销售或其他处置。
- 乙方转让其未必拥有权利的客户信息、公开政策文件、第三方材料和个人信息。
- 注销完成后 15 个工作日内删除或匿名化全部相关个人信息。
- 债务人还款后立即销毁个人隐私信息。

这些规则与结算、税务、审计、争议处理、侵权举证、反舞弊和法定留存可能冲突。个人信息也不能简单按知识产权转让处理。

**建议**：拆分为“任务成果著作权/使用许可”“第三方材料来源保证”“个人信息处理授权”“法定留存例外”“商业化使用范围”五类条款；为每类数据确定处理目的、合法性基础、最小范围、保存期限、访问角色和销毁方式。

### 4.4 准入条件过宽且不可执行

“有涉诉记录不得注册”“涉诉等不良记录”覆盖范围过大，可能把普通民事纠纷、原告身份或已结案件一并排除；“失信”也需要区分失信被执行人、一般信用记录和内部违约。

**建议**：将准入条件改成可验证的枚举和期限规则，例如记录类型、裁判/执行状态、发生时间、岗位相关性、人工复核人和申诉通道，避免仅用模糊关键词自动拒绝。

### 4.5 保险责任口径冲突

岗位与计酬制度称平台统一购买职业责任险、数据泄露责任险、调查失误损失险和人身意外险；众包服务协议只明确统一购买人身意外险，又建议乙方自行投保其他险种。

**建议**：在上线前定版投保人、被保险人、保障岗位、地域、免责条款、单次/累计保额、保费承担、事故报案和理赔协作流程。系统需要记录保单版本、适用任务和有效期，不能只保存一个“已投保”布尔值。

### 4.6 先到先得缺少可执行的确权规则

当前规则只说明以系统上传时间戳判定第一名，尚缺：

- “同一线索/客户/项目”的规范化主键和查重范围
- 文本近似、同人异名、同资产多证号、同客户多联系方式的合并规则
- 服务器接收时间、上传完成时间还是审核通过时间作为确权时间
- 并发提交时的数据库原子锁和唯一约束
- 断点重传、重复请求、客户端重试的幂等键
- 首传内容无效、缺证、撤回、补充、纠错和被驳回后的权益变化
- 机器建议重复但人工裁定不重复时的恢复机制
- 跨公司、跨案件、跨任务的查重边界

**建议**：确权结果必须来自确定性事务。LLM/向量相似度只能产生“疑似重复”候选，不能直接决定资金权益。

### 4.7 计酬与贡献归因不能复算

发现的具体问题包括：

- “固定证据 16%～10%”区间倒置，无法判断是笔误还是两类费率。
- 净回款列出部分扣减项，但没有成本发生时间、审核状态、税额、分摊和冲正规则。
- 同一回款由多条线索、多名人员、多阶段建言共同促成时，缺少贡献归因顺序。
- AI 穿透发现、AI 抓取、AI 报备均“比照计酬”，但没有自然人收款主体，也没有定义人类对 AI 结果的有效增量。
- S 级政策建言存在“项目跨度超过 18 个月”与“距回款超过 24 个月”的双重条件，触发关系不清。
- 多条建言的 0.5% 总上限、首条 60%/第二条 25%/其余 15%与单条 0.3%之间缺少完整计算例子。
- 退款、坏账、撤销认定、重复支付、税费调整和申诉改判后的冲正机制未定义。

**建议门禁**：先形成可执行的计酬规则表和至少 20 个边界案例。所有费率按版本管理，接单或投稿时冻结规则快照；结算采用不可变分录，调整只新增冲正分录，不能覆盖历史金额。

### 4.8 匿名、敏感信息与可见范围互相冲突

需要统一优先级的规则包括：

- 全员匿名，只展示岗位和系统数字 ID。
- 资深专家可读全部资料。
- 仅总经理可见敏感文件全文。
- 项目经理及以上经总经理授权可见脱敏前信息。
- 众包人员只能查看自己提交的敏感信息。
- 所有人只能下载脱敏文件。

现有 AI Hunter 的权限模型主要是“模块权限 + 报告段权限 + 案件 owner/member”，不能表达“同一案件中只能看自己投稿的某一对象、某些字段、某个版本”。

**建议**：新增以 `tenant + case + object + field_classification + relationship + purpose` 为条件的对象级/字段级授权；实名信息独立保管，业务表只使用匿名贡献者 ID。查看实名、查看原文、下载和授权变更都进入审计日志。

### 4.9 盲测需要独立隔离域

材料规定盲测内容暂不入库、不触发联动、不计酬，但项目组可以查阅，验证通过后又需要正式入库并补发报酬。“不入库”与“可查阅、可归档、可转正”不能同时成立。

**建议**：将其解释为“不进入权威业务库”，而不是“不持久化”。盲测池应有独立存储、权限、版本和状态，转正时通过受控投影生成正式投稿/claim，并保留来源关联。

### 4.10 现场采集的安全与证据要求不足

不动产和煤矿拍照规范描述了拍摄内容和画质，但缺少：

- GPS、服务器时间、设备 ID、拍摄人、拍摄方向、EXIF、文件哈希、采集会话
- 照片与资产、证照、检查点、任务和投稿版本的关联
- 感知哈希去重、模糊/过曝检测、EXIF 异常和后期编辑检测
- 煤矿井下资质、安全培训、入井审批、防爆设备、陪同人和离线采集流程
- 原始照片、展示图、下载图的水印策略

“现场原始照片无水印”与“下载必须可追溯”并不冲突，正确做法是保存无水印原件，展示或下载时生成动态水印/暗记副本，原件只对受控角色开放。

## 6. Excel 资产表评审

### 6.1 结构检查结果

8 份工作簿均为单工作表，已用区域为 10 列、25 至 40 行。检查结果一致：

- 0 个公式
- 0 个数据校验
- 0 个条件格式
- 0 个正式 Excel Table 对象
- 0 个图表或其他绘图对象

因此这些表目前是**纸面采集清单**，不是可直接执行的数据模型或评价引擎。

### 6.2 共性问题

1. “行次”只是版面序号，不是稳定字段编码；模板增删一行就会改变含义。
2. “数据来源”是自由文本，无法关联文件、页码、照片、采集时间和证据审核状态。
3. 没有数据类型、必填性、枚举、数值范围、精度、单位换算、条件显示和跨字段校验。
4. 没有 `tenant_id`、`case_id`、`asset_id`、`task_id`、`submission_id`、版本、状态、采集人、复核人和时间戳。
5. 红色字段和个别蓝色字段没有图例，无法判断颜色表示必填、风险、自动计算还是重点核验。
6. 租售比、吨煤总成本、吨煤毛利等可计算字段仍要求人工填写，容易出现口径不一致。
7. 每个资产类型复制一份完整表，公共字段重复维护，后续变更容易漂移。

### 6.3 具体字段问题

| 模板 | 问题 | 建议 |
|---|---|---|
| 工业土地 | “容积率”在专项和基础信息中重复；“绿地率/绿化率”含义可能重复 | 确认是否同一指标；同一语义只保留一个字段编码 |
| 停车库 | “是否独立产权”在专项和权属信息中重复 | 合并或明确一个是车位、一个是项目层级 |
| 停车库 | “物业费”单位为“元/㎡·个”，“单个车位尺寸”单位为 m | 确认应为元/个·月、元/㎡·月或其他；尺寸应拆长宽或使用㎡ |
| 煤矿表一 | “矿区面积”单位写作 `k㎡` | 建议统一为 `km²`，数据库保存标准单位码 |
| 煤矿表一 | 发热量为 `cal/g` | 确认业务惯用口径，统一显示和换算规则 |
| 煤矿表二 | 工作表名仍是“采矿许可证信息评价表”，实际包含经济性、市场、处置和估值 | 改为与内容一致的模板名称和稳定模板编码 |
| 煤矿两表 | 项目位置仍含楼栋号、单元号、门牌号 | 按矿区坐标、矿区范围、井口/场区地址重构，不沿用住宅地址模型 |
| 全部 | 数据来源枚举只有文档末尾文字提示，无下拉或证据引用 | 使用来源类型枚举，同时强制关联 `evidence_id` |

### 6.4 推荐的表单模型

不要把 8 个 Excel 直接翻译成 8 张宽表。建议采用“模板目录 + 字段目录 + 版本化投稿 + 字段值 + 证据”的模型：

```text
crowd_form_template
  -> crowd_field_catalog
  -> crowd_submission (one submission, one immutable version)
      -> crowd_submission_value
      -> crowd_evidence
      -> crowd_review_decision
```

字段目录至少包含：

- 稳定字段码、中文名、所属资产类型和分组
- 数据类型、单位码、精度、是否必填、枚举值
- 最小/最大值和跨字段校验规则
- 证据要求、采集方式和敏感级别
- 自动化方式：规则计算、AI 建议、人工填写
- 生效版本、停用状态和排序

可以参考现有 `sql/screening_tables.sql` 的成熟模式：目录项稳定编码、评分卡多版本、机器建议与人工确认分列、修改原因必填、证据引用单独保存、参数按版本冻结。但众包投稿应新建自己的业务表，不直接复用筛选评分卡表。

## 7. 推荐架构

### 7.1 可选方案

| 方案 | 说明 | 优点 | 风险/代价 | 结论 |
|---|---|---|---|---|
| A. 独立众包服务/业务后端模块 | 在事务型业务后端建设众包域，AI Hunter 通过 API/事件消费审核结果 | 权限、结算、并发和发布可独立治理；边界清晰 | 新增服务契约、部署和运维 | **推荐，适合正式运营** |
| B. 在本仓库新增确定性 `crowd` 模块 | 使用 FastAPI router/service/repository/worker，但不进入 LangGraph 状态机 | MVP 部署较简单，可复用当前认证和数据访问 | 与编排服务耦合，后续拆分成本高 | 可用于受控试点，需预留迁移边界 |
| C. 直接新增 LangGraph 众包节点 | 把接单、审核、结算作为图节点 | 表面接线快 | 重试、并发、长事务、权限和资金一致性不可控 | **不建议** |

方案 A 与 B 需要业务方根据部署、团队所有权和预期规模确认后再实施；无论选哪种，权威状态都必须在事务数据库中，LangGraph 只消费结果。

### 7.2 推荐组件

```text
Identity & Compliance
Task Marketplace
Submission & Evidence
Deduplication & Entitlement
Review & Adjudication
Pricing & Reward Ledger
Referral / Quality Chain
Dispute / Exit / Retention
Outbox & AI Hunter Projection
```

### 7.3 核心状态机

```text
Task
draft -> published -> claimed -> submitted -> reviewing
      -> accepted / rejected / disputed
      -> settled / closed / cancelled

Submission
draft -> submitted -> dedup_pending
      -> review_pending / blind_pool
      -> accepted / rejected / correction_pending / superseded

Reward
accrued -> approved -> payable
        -> paid / reversed / held

User
pending_verification -> active
        -> suspended / inactive / cancellation_pending
        -> cleared / rejected
```

每个状态转换必须定义：允许角色、前置条件、幂等键、时间戳、审计事件、通知、超时动作和是否可逆。

### 7.4 事务与事件原则

1. 接单、确权、审核、计酬和状态迁移使用数据库事务与唯一约束。
2. 所有外部写请求使用客户端请求 ID + 服务端幂等键。
3. 关键业务事件写入 outbox，再由持久化 worker 投递；不能依赖进程内线程池保证结算或投影不丢失。
4. 规则、费率、模板和权限均版本化，业务记录冻结当时快照。
5. 结算台账只追加，不覆盖；撤销和改判用 reversal 分录。
6. LLM 输出保存模型、提示版本、输入摘要、置信度和人工决定，但不得成为资金唯一裁决依据。

## 8. 与现有 AI Hunter 的复用和缺口

| 现有能力 | 可复用部分 | 不能直接复用的部分 | 推荐接入方式 |
|---|---|---|---|
| 认证、多租户、案件成员 | 公司、用户、案件 owner/member 基础身份 | 投稿对象级、字段级、实名解密和用途授权 | 扩展 ABAC/关系授权，不修改报告段权限冒充对象权限 |
| `task_api` / `task.write` | 审核通过后生成内部 SOP 督办任务 | 抢单、锁单、投稿、质控、结算、申诉 | 众包任务独立模型；必要时投影成内部督办任务 |
| `/files` 与 ingest | 文件存储、SHA256 文件去重、OCR、材料事件 | 语义线索查重、权益确权、盲测隔离 | 投稿先进入隔离区，审核通过后生成正式材料事件 |
| 知识图谱与证据链 | claim/evidence、页码、bbox、引用回源、supersede | 未审核投稿不能成为权威 claim | accepted 事件触发标准 claim/material 投影 |
| 权威订正 | 人工批准后的权威修正与历史追溯理念 | 外部投稿不等同于权威订正 | 仅审定通过且需要覆盖时，由内部授权流程生成订正 |
| 回款与进度 | 案件实收、预期回款、报告引用 | 成本台账、净回款、贡献归因、奖励和税务 | 读取已确认实收，新增独立成本与奖励台账 |
| screening 评分卡 | 字段目录、版本、建议/确认分离、证据 refs、参数快照 | 业务对象和状态不同 | 复用设计模式，不共用实体表 |
| LangGraph/SSE/checkpointer | 报告重算和长任务进度展示 | 众包权威状态、资金台账、接单锁 | 只承接 accepted 后的 AI 处理与结果展示 |

特别注意：当前 `task.write`、`material.upload` 仍在分层路由 Phase 2.5.4 待迁移范围内。众包模块不应把这部分未完成的写入迁移当作已稳定底座。

## 9. 分阶段落地建议

### 阶段 0：规则与法务定版

交付物：

- V1.1 权威文件目录与冲突裁决顺序
- 角色、任务、数据分级和权限矩阵
- 计酬规则表、净回款口径和边界案例集
- 个人信息处理清单与留存期限表
- 现场调查红线、安全与保险方案
- 确权查重规则和争议裁决 SLA

退出条件：本报告第 10 节的 P0 事项全部有责任人和书面结论。

### 阶段 1：事务核心与受控试点

范围：身份准入、任务发布/接单、版本化投稿、证据上传、C/B/A 质控、审计事件、对象级权限和 outbox。

暂不做：自动结算、复杂 S 级分成、AI 自动确权、跨公司任务市场。

### 阶段 2：查重、确权与争议

范围：规范化 fingerprint、相似候选、原子确权、纠错/补充、盲测池、异议、裁决和恢复。

上线前必须做并发压测和负向权限测试。

### 阶段 3：计酬与结算

范围：规则版本、费率快照、成本分录、净回款、贡献归因、应计/审批/应付/支付/冲正、税务和对账导出。

建议先上线固定价任务，再逐步开放回款分成和 S 级政策建言，避免一次引入全部资金复杂度。

### 阶段 4：AI Hunter 联动

范围：审核通过的投稿投影为 material/claim，触发图谱增量对账、报告重算、任务生成和回款复盘；AI 输出必须保留人工确认卡口。

## 10. 必须由业务/法务拍板的事项

### P0 决策清单

1. 最终签约主体、平台运营主体、数据处理者和收付款主体分别是谁。
2. 众包 V1 是否正式取代 0624 旧材料；客户报备有效期是否最终为 180 天。
3. 伯乐只承担引荐 + 质控，还是仍存在独立推广分成；两者能否并存。
4. 蝴蝶效应及前瞻研究岗位是否纳入服务协议，准入条件是什么。
5. 自由接单、拒单、响应承诺、任务量和暂停/清退如何设计，才能与真实承揽关系一致。
6. 哪些涉诉/失信记录构成准入限制，核验来源、期限和申诉规则是什么。
7. 职业责任险、附加险和意外险由谁购买，覆盖哪些任务和人员。
8. 自创成果、第三方资料、公开信息、客户数据和个人信息分别授予平台何种权利。
9. 是否允许销售上传数据；若允许，具体数据类型、目的、对象和单独同意机制是什么。
10. 注销、还款、争议、税务、审计和诉讼场景下的数据留存期限分别是多少。
11. 数据分级与岗位权限冲突时，以哪条规则优先；谁能授权查看实名和原件。
12. 先到先得的对象主键、确权时间点、查重范围和首传无效后的权益如何处理。
13. AI 发现是否产生任何个人计酬；人工验证或加工达到什么程度才算可计酬增量。
14. “固定证据 16%～10%”的正确费率和档位是什么。
15. 净回款的全部扣减项、成本审核、分摊、税费和冲正规则是什么。
16. 多线索、多建言、多人员和跨阶段贡献如何归因；总上限如何计算。
17. S 级 18/24 个月衰减条件和多建言分配公式是什么。
18. 清退申诉期间账号、在途任务、证据访问和未结算报酬如何处理。
19. 盲测期、转正标准、可见范围、失败归档和补发计酬如何定义。
20. 煤矿现场任务所需资质、安全培训、设备和审批证明是什么。

在上述事项未定前，技术团队可以做原型和数据字典，但不应固化生产 DDL、结算公式或自动清退规则。

## 11. 验收标准建议

### 11.1 规则可执行性

- 每种任务有稳定任务码、成果定义、验收标准、计酬规则版本和责任角色。
- 每条状态转换有权限、前置条件、SLA、通知和失败处理。
- 每个资金公式都有输入、单位、舍入、上限、例外和可复算样例。

### 11.2 数据与证据

- 每个投稿和证据有租户、案件、资产、任务、贡献者匿名 ID、版本、服务器时间和哈希。
- 图片保留原件并生成带水印派生件；原件访问单独授权。
- 资产字段使用稳定字段码、类型和单位；所有关键值可回源到证据。
- 审核通过、驳回、修改和 supersede 均保留完整历史。

### 11.3 并发与幂等

- 同一对象并发投稿只能产生一个有效首权结果。
- 网络重试、断点续传和重复回调不会重复计酬、重复投影或重复支付。
- 事件投递失败可重试，可定位，最终能与源记录对账。

### 11.4 权限与隐私

- 跨公司、跨案件、跨投稿、跨字段的负向权限测试全部通过。
- 众包人员只能读取授权任务和自己可见的投稿版本。
- 实名解密、敏感原文查看、下载和授权变更都有审计日志。
- 注销不会破坏依法必须保留的结算和争议证据，也不会继续暴露非必要数据。

### 11.5 结算

- 任一支付金额都能回放到任务、投稿、审核决定、费率版本、回款和成本分录。
- 改判、退款和重复支付通过冲正分录处理，历史不可被覆盖。
- 结算汇总能与支付平台、税务记录和总账对账。

### 11.6 AI Hunter 联动

- 未审核、盲测中或被驳回的数据不会进入权威 claim 和正式报告。
- accepted 投稿投影失败可重试且不重复写入。
- 报告重算能够引用投稿证据，并区分原始材料、众包采集、AI 建议和人工审定。

## 12. 文档工程化建议

这些问题不阻塞业务讨论，但应在 V1.1 定版时一并治理：

1. 10 份 Word 的段落样式均为 `Normal`，缺少可生成目录和导航的语义化标题样式。
2. 清退制度用 Markdown 管道符模拟表格，应改成真正的 Word 表格。
3. 存在“包人员清退”“台可以”“一 次”等文字错误。
4. 文件名含 `(1)`、编号前缀重复，缺少统一版本、状态和生效日期。
5. 资产表红色/蓝色字段无图例，无法确定业务含义。
6. 建议新增一份机器可读的数据字典和规则目录，不再只依赖正文描述。

## 13. 最终建议

众包 V1 的正确建设顺序是：

```text
规则定版与法务审查
  -> 事务型众包域和对象级权限
  -> 确权/质控/争议
  -> 结算台账
  -> 审核结果投影到 AI Hunter
```

当前最值得保留的设计是“先到先得竞争 + C/B/A 实际质控 + 审核后联动 AI Hunter”；当前最需要避免的是把 Word 条款直接翻译成状态枚举、把 8 个 Excel 直接翻译成宽表、把未经审核的外部投稿直接写进权威报告，以及用 LangGraph/checkpointer 承载接单和资金状态。

完成第 10 节决策后，再产出正式的《众包 V1.1 领域模型与接口设计》，届时才能可靠确定服务归属、DDL、API、事件契约、权限矩阵和测试计划。
