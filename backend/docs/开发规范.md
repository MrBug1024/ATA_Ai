# 开发规范

本文档记录本项目以及相关上下游项目协同开发时必须遵守的约定。后续新增规范可继续追加到本文档，并同步写入长期记忆。

## 1. 高风险操作授权

以下操作必须先获得用户明确授权，不能自行执行：

- 修改数据库数据的操作。
- 删除文件的操作。
- 使用系统命令执行删除、清理、重置等具有破坏性的操作。

## 2. 数据库结构变更说明

新增数据库表、修改数据表列时，必须写清楚注释：

- 表必须有清晰的表描述。
- 新增字段必须有 `COMMENT` 或等价说明。
- 修改字段时必须说明字段语义、用途和影响范围。

## 3. 疑问与方案确认

项目中存在不清楚的问题、业务含义、实现方案或设计思路时，不能臆测用户意图。

处理原则：

- 先把疑问、可选方案、影响面说明清楚。
- 等用户确认方向后再执行。
- 避免因为假设错误导致项目方向跑偏。

## 4. 多方案决策

涉及多套方案、多种技术路线或业务思路时，不能由 Codex 自行拍板。

处理原则：

- 列出候选方案。
- 说明每个方案的优缺点、风险和适用场景。
- 用户确认方案后再进入实现。

## 5. 规划文档沉淀

涉及修改问题的整体方案、新增模块、新增业务线时，必须新增 Markdown 文档落到 `docs/` 目录，便于后续梳理、评审和对齐进度。

处理原则：

- 先在 `docs/` 下新增规划 / 设计 / 落地方案文档。
- 文档应说明背景、目标、范围、关键决策、实施阶段、影响文件和验收标准。
- 代码实现应与该文档保持一致；后续方案变化时同步更新文档。

## 6. Git 提交描述

后续推送远程仓库前的 commit message 必须使用中文描述，便于项目进度回看和非英文协作者理解。

处理原则：

- commit message 用简洁中文说明本次变更目的。
- 可以保留英文技术名词、配置名、接口名和文件名。
- 不使用只有英文的提交描述。

## 7. 协作审计与 PR Review

对话中的修复过程必须带 `PR review` / `change review` 视角，不能只在最终回复里说“已修复 / 测试通过”。

处理原则：

- 修复前先说明风险点、判断依据、改动范围，再说明修复方案。
- 每次编辑写入后，必须立即给出 `Review checkpoint`：列出已编辑文件，贴出关键真实 diff hunk（带增删行标记），并用 1-3 句解释该 diff 为什么解决问题。
- 最终回复必须包含可审计信息：改了哪些文件、关键 diff / 行为变化、验证命令与结果、未验证项 / 剩余风险。
- 涉及关键逻辑时，必须引用具体文件位置或贴出对应 diff 片段，让用户能看到修复过程中的 review 审计。
- 如果变更影响线上行为（模型 provider、SSE、持久化、任务创建、权限、DDL 等），必须说明回滚点和是否已重启服务 / 是否已真实冒烟。
- 若工作区存在非本次修改的本地改动，最终回复中必须区分“本次改动”和“既有 / 用户改动”，避免把无关 diff 归因到本次修复。
