# 操作员链路改造计划的代码落地方案

## 1. 背景与问题

当前操作员上传案件材料的主入口在 [ai_hunter/app/api/routes_files.py](/Users/liuyize/NpaLangG/ai_hunter/app/api/routes_files.py) 中，接口在接收上传后会同步执行 `ingest_graph.invoke(...)`。这意味着前端必须等待以下链路全部完成，才能进入下一步：

1. 文件基础校验
2. 对象存储写入
3. OCR / 文本抽取
4. 聚合文本
5. `parseDocument` 远程解析与业务入库
6. `load_chunks`
7. 图谱抽取、归一化、去重、持久化
8. 增量对账与图谱摘要生成

现状问题：

1. 上传接口是长事务，前端等待时间过长。
2. 用户必须等待整条链路跑完，无法先继续后续操作。
3. `ingest_graph` 内部既有业务入库，也有图谱增强，职责耦合过深。
4. 非文本文件存在两次 OCR/版面解析调用的风险：
   - `ingest_graph.filter_files` 产出纯文本
   - `load_chunks` 再做 layout OCR 产出 page/chunk
5. 即使图谱链路失败，也会拖慢甚至阻塞操作员上传闭环。

本方案的核心目标不是先把每个节点极限提速，而是先把“前端同步等待整条链路”改造成“快速受理 + 后台异步处理 + 状态可观测”。

---

## 2. 改造目标

### 2.1 业务目标

1. 操作员上传后应尽快获得“系统已接收”的反馈。
2. 前端不再阻塞等待完整 OCR、parse、图谱链路结束。
3. 操作员可以基于批次状态继续后续操作。
4. 图谱与对账结果改为后台渐进完成。

### 2.2 技术目标

1. 上传接口从同步长请求改为 `202 Accepted` 模式。
2. 建立稳定的后台任务状态机，复用现有 `material_event` / `upload_batch`。
3. 将上传链路拆分为：
   - 同步受理阶段
   - 后台业务解析阶段
   - 后台图谱增强阶段
4. 引入 OCR 中间产物缓存，复用文本与布局结果。
5. 为后续独立 worker / 队列化保留接口，不把进程内后台任务当最终形态。

## 4. 总体改造策略

本次改造采用“三段式执行模型”。

### 第一段：同步受理阶段

由上传接口同步完成，仅保留必要且廉价的工作：

1. 基础参数校验
2. 文件大小/数量校验
3. `doc_category` 校验
4. 文件写入对象存储
5. 创建/更新 `upload_batch`
6. 创建 `material_event`
7. 返回 `202 Accepted`

这一阶段不再执行：

1. OCR
2. parseDocument
3. 图谱抽取
4. 图谱对账

### 第二段：后台业务解析阶段

由后台异步执行，负责让“本批材料进入案件业务语义层”：

1. OCR / 文本读取
2. 文本聚合
3. 债务人名称推断
4. `parseDocument` 调用
5. 业务入库
6. 更新 `material_event` 状态

这是“用户可继续工作”的关键阶段，但不阻塞上传接口返回。

### 第三段：后台图谱增强阶段

由后台异步执行，负责增强型能力：

1. `load_chunks`
2. 实体/关系/断言抽取
3. 归一化
4. 去重
5. 图谱持久化
6. 增量对账
7. 图谱摘要

这部分完全不阻塞操作员下一步操作。

## 5. 推荐分期

### Phase 1：上传接口快速返回

目标：尽快消除前端长等待。

做法：

1. 上传接口只做同步受理
2. 写入 `material_event=status=received`
3. 提交后台任务
4. 直接返回 `202`

结果：

1. 前端等待时间从“整条链路耗时”缩短为“文件上传 + 存储耗时”
2. 用户体感立即改善

### Phase 2：整条 ingest 先整体挪到后台

目标：最小改动完成异步化。

做法：

1. 暂时不立刻大拆图
2. 后台任务先直接跑当前 `ingest_graph`
3. 前端通过状态接口轮询

结果：

1. 代码改动较小
2. 尽快把请求-响应模型改掉

### Phase 3：拆分后台优先级

目标：减少后台关键路径耗时。

做法：

1. 把 `parse_document_and_ingest` 与 `knowledge_graph_graph` 解耦
2. 后台任务拆成两个阶段任务：
   - 业务解析任务
   - 图谱增强任务

结果：

1. 可更清楚地表达状态
2. 图谱失败不影响业务入库结果

### Phase 4：OCR 中间产物缓存复用

目标：消除重复 OCR。

做法：

1. 第一次 OCR 后落中间产物
2. `load_chunks` 优先读缓存
3. 缓存失效或缺失时才回源 OCR

结果：

1. 后台链路总体耗时下降
2. OCR 服务压力下降

1. `received`

3. `ocr_running`

## 6.5 OCR 中间产物缓存

建议新增文件：

1. `ai_hunter/app/services/ocr_artifact_store.py`

职责：

1. 以文件 hash 为键缓存 OCR 中间产物
2. 支持文本、页信息、block、原始响应
3. 支持对象存储引用或 heavy payload 引用

建议数据结构：

```json
{
  "file_sha256": "xxx",
  "file_name": "sample.pdf",
  "content_type": "application/pdf",
  "ocr_provider": "ocr.rhzy.ai",
  "ocr_version": "v1",
  "text": "...",
  "pages": [],
  "blocks": [],
  "page_width": 0,
  "page_height": 0,
  "raw_response_ref": "heavy-payload:xxx"
}
```

### 缓存使用方式

1. `filter_files` 处理非文本文件时，优先读取 OCR artifact
2. 缓存缺失时调用 OCR，并写入 artifact
3. `load_chunks` 构造 layout 数据时优先读取 artifact
4. 只有 artifact 缺失时才调用 `_load_layout_result(...)`

### 相关改造点

文件：

1. [ai_hunter/app/subgraphs/ingest_graph.py](/Users/liuyize/NpaLangG/ai_hunter/app/subgraphs/ingest_graph.py)
2. [ai_hunter/app/graph/nodes/load_chunks.py](/Users/liuyize/NpaLangG/ai_hunter/app/graph/nodes/load_chunks.py)

注意：

1. 不能只缓存纯文本，必须同时缓存 layout 信息
2. 大尺寸 `raw_response` 不建议直接塞数据库，优先存对象存储或 heavy payload

## 6.6 load_chunks 复用 OCR artifact

当前 [ai_hunter/app/graph/nodes/load_chunks.py](/Users/liuyize/NpaLangG/ai_hunter/app/graph/nodes/load_chunks.py) 在非文本文件上直接调用 `_load_layout_result(...)`。

建议改造为：

1. 先尝试按 `file_sha256` 查 OCR artifact
2. 若已有完整 layout，直接复用
3. 若只有文本没有 layout，则补充 layout
4. 若完全没有 artifact，才回源 OCR

建议伪代码：

```python
artifact = get_ocr_artifact(file_sha256)
if artifact and artifact_has_layout(artifact):
    layout_result = build_layout_result_from_artifact(artifact)
else:
    layout_result = _load_layout_result(ocr_service, file_item, extension)
    save_ocr_artifact(...)
```

## 8. 建议接口兼容策略

为降低联调风险，建议分两步兼容：

### 方案 A：原接口切换为异步返回

优点：

1. 改动集中
2. 前端最早收益

缺点：

1. 旧前端若强依赖同步返回完整 parse 结果，会受影响

### 方案 B：保留旧接口，新增异步版本

例如新增：

1. `POST /files/upload-and-ingest-async`

优点：

1. 联调期间风险更低
2. 新旧前端可并存

缺点：

1. 会短期保留两套行为

建议：

1. 如果前端已进入联调且变更窗口小，优先方案 B
2. 如果前后端可同步修改，优先方案 A

## 9. 风险与注意事项

### 9.1 幂等性

后台任务必须基于以下键保证幂等：

1. `upload_batch_id`
2. `material_event_id`
3. `file_sha256`

同一批次重复触发时：

1. 已完成阶段不得重复写入造成脏数据
2. 图谱重复跑要么幂等，要么被状态拦截

### 9.2 失败恢复

必须支持：

1. 任务执行中进程重启
2. OCR 失败可重试
3. parseDocument 超时可重试
4. 图谱阶段失败不影响已完成的 parse 结果

### 9.3 大对象存储

OCR artifact、layout、原始响应可能很大：

1. 不建议直接塞响应
2. 不建议大量塞普通关系表
3. 建议对象存储 + 引用字段

### 9.4 观测性

日志必须带：

1. `upload_batch_id`
2. `material_event_id`
3. `case_id`
4. `stage`

便于联调期间快速定位卡点。

## 10. 验收标准

### 第一阶段验收

1. 上传接口返回 `202`
2. 返回中包含 `upload_batch_id`、`material_event_id`
3. 前端不再等待 OCR / parse / 图谱完成
4. `material_event` 可查询当前阶段

### 第二阶段验收

1. 后台任务能完成 parse 与图谱链路
2. `completed` / `failed` 状态准确
3. 失败时错误信息可追踪
4. 图谱阶段失败不导致上传接口失败

### 第三阶段验收

1. `load_chunks` 可复用 OCR artifact
2. 同一文件不再重复 OCR 两次
3. 后台链路总体耗时下降

---

## 11. 推荐实施顺序

建议严格按以下顺序推进：

1. 改上传接口为 `202`
2. 建立后台任务入口与状态更新收口
3. 先把现有整条 ingest 搬到后台
4. 拆分 parse 阶段与图谱阶段
5. 引入 OCR artifact 缓存
6. 补幂等、重试、恢复逻辑
7. 补测试与联调文档

这样做的原因是：

1. 第一时间解决前端等待问题
2. 先改请求模型，再做链路内部优化
3. 避免一开始就做大范围重构，影响联调节奏

---

## 12. 本方案的最终决策建议

建议本项目按以下原则执行：

1. 上传接口不再承担完整摄入链路
2. `material_event` 成为前后端联调的统一进度源
3. parse 与图谱增强解耦
4. OCR 结果作为中间产物缓存复用
5. 短期允许进程内任务执行器过渡，但设计上要为独立 worker 留出边界

这份方案优先解决“操作员一直等待”的体验问题，同时不会破坏后续把任务系统升级成独立 worker 的演进路线。
