## 1. 设计目标与核心取舍

会话层要同时满足两个互相矛盾的诉求，因此采用**双轨存储 + 物理隔离**：

| 诉求 | 手段 |
|---|---|
| 喂给 LLM 的上下文要**省 token**、可截断 | LangGraph `messages` 只放脱水摘要；长报告走 heavy-payload，靠 `final_report_ref` 引用 |
| 给前端的历史要**全文可回显**、查询快、schema 稳定 | 专用 `conversation_messages` 表存全文 + 角标快照，与 checkpointer 解耦 |

由此衍生三条原则：

1. **长报告永不进 `messages`**：报告正文与对话记忆物理隔离（[memory.py:106-112](../ai_hunter/app/graph/nodes/memory.py#L106)）。`messages` 里 assistant 仅留一行 `summary_line`（如 `intent=full_audit | case_id=116 | report_generated chars=8421`）。
2. **单写者（single-writer）**：每轮只有 `persist_conversation_memory` 一个节点落库，先写 `conversation_messages` 成功，再返回 state 更新给 LangGraph；写失败则节点抛错、checkpoint 不前移，保持一致（[conversation_message_repo.py:3-13](../ai_hunter/app/repositories/conversation_message_repo.py#L3)）。
3. **幂等可重试**：`conversation_messages` 写入用 `ON CONFLICT DO NOTHING`；`conversation_log`（checkpoint 内）用按 `id` 去重的 reducer。

## 2. 三套存储载体

```
┌─────────────────────────────────────────────────────────────────┐
│ ① LangGraph checkpoints（public.checkpoints / checkpoint_blobs）  │
│    - channel_values：整个 AuditGraphState 快照（含 messages、       │
│      memory_summary、current_case_id、final_report_ref…）          │
│    - 由 PostgresSaver / AsyncPostgresSaver 读写                     │
│    - 用途：会话状态续跑、线程列表/详情、legacy 消息回退             │
│    - 软删除：deleted_at（add_soft_delete_to_checkpoints.sql）       │
├─────────────────────────────────────────────────────────────────┤
│ ② conversation_messages（专用消息表，与 checkpointer 解耦）         │
│    - 一行一条消息（user / assistant），存全文 content + 角标快照     │
│    - 用途：历史消息/轮次查询（前端刷新会话）、幂等缓存命中           │
│    - 软删除：deleted_at（与 checkpoints 对齐）                       │
├─────────────────────────────────────────────────────────────────┤
│ ③ heavy_payload_store（三层：进程→Redis→Postgres）                  │
│    - 长报告正文等大对象，messages/表里只存 final_report_ref          │
└─────────────────────────────────────────────────────────────────┘
```

### 2.1 `conversation_messages` 表结构

来自 [sql/conversation_messages.sql](../sql/conversation_messages.sql)：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL PK | 自增主键 |
| `thread_id` | TEXT | 会话线程 ID（= LangGraph thread_id） |
| `turn_id` | TEXT | 轮次 ID，格式 `{hash}_user` / `{hash}_assistant` |
| `role` | TEXT | `user` / `assistant` / `system`（CHECK 约束） |
| `content` | TEXT | 完整内容；assistant 为展示给用户的答复全文（报告全文即在此） |
| `intent` | TEXT | 本轮意图：full_audit / drilldown / re_audit / review / ingest |
| `case_id` | INT | 关联案件 |
| `final_report_ref` | TEXT | 本轮报告的 heavy-payload 引用（点角标拉证据用） |
| `uploaded_files` | JSONB | user 携带的附件列表；assistant 为 `[]` |
| `graph_context` | JSONB | assistant 的图谱与路由快照：`{route_decision, trace_items, citation_coverage, unresolved_relations, unresolved_claims}`；user 为 `{}` |
| `version` | INT | assistant 版本，1=首次，2+=重新生成 |
| `created_at` | TIMESTAMPTZ | 入库时间 |
| `deleted_at` | TIMESTAMPTZ | 软删除时间，NULL=存活 |

索引/约束：

- `idx_conv_msg_user_unique`：`(thread_id, turn_id) WHERE role='user' AND deleted_at IS NULL` —— **保证每轮 user 唯一**，是幂等的关键。
- `idx_conv_msg_thread_created`：按 `(thread_id, created_at)` 查存活消息。
- `idx_conv_msg_case_id`：按案件查。

> `graph_context` 是 issue #8 的产物：把本轮 `/chat/invoke` 当时的角标证据预览 / 覆盖率警告条 / 待补件 badge 一并落库，使**刷新历史会话时这些前端附属信息不丢失**。历史行（issue #8 之前）与所有 user 行 `graph_context` 为空，读取侧 `_flatten_graph_context` 兜底为空列表/字典，契约稳定（[conversation_service.py:20-34](../ai_hunter/app/services/conversation_service.py#L20)）。

| 字段 | reducer | 作用 |

## 3. 三套 ID 体系

| ID | 来源 | 生成方式 | 用途 |
|---|---|---|---|
| `thread_id` | 前端传入（多轮保持同一个） | 前端自定 | 会话线程主键，贯穿 checkpoint / messages / advisory lock |
| `client_turn_id` | 前端可选传入 | 前端自定 | **幂等键**：同一条用户操作重复提交时命中缓存，不重复跑图 |
| `turn_id` | 后端确定性生成 | 见下 | 把一轮的 user + assistant 串起来；`conversation_messages.turn_id` = `{turn_id}_user` / `{turn_id}_assistant` |

`turn_id` 的确定性派生（[memory.py:124-135](../ai_hunter/app/graph/nodes/memory.py#L124)）：

- 传了 `client_turn_id`：`turn_id = sha256(f"{thread_id}:{client_turn_id}")[:16]`
- 没传：`turn_id = sha256(f"{query}:{case_id}:{intent}:{len(messages)}")[:16]`

> 确定性意味着同一轮重算得到同一 `turn_id`，配合唯一索引与 `ON CONFLICT DO NOTHING` 实现幂等。

advisory lock 的 key 也由 `thread_id` 派生（[pg_lock.py:12-16](../ai_hunter/app/utils/pg_lock.py#L12)）：`sha256(thread_id)` 前 8 字节取 63-bit 正整数。

## 4. 写入链路：`persist_conversation_memory`

主图最后一个节点（[memory.py:82-223](../ai_hunter/app/graph/nodes/memory.py#L82)）。空 query 直接跳过。流程：

```
1. 取本轮要点：query / case_id / debtor / parse_summary / final_report / agent_output / intent
2. 组 summary_line（脱水）：intent=… | case_id=… | (report_generated chars=N | agent=… | ingest=…)
   full_answer = final_report or agent_output or summary_line   ← 落 conversation_messages 的 content
3. 组 graph_context 快照（trace_items / citation_coverage / unresolved_*）
4. 生成 turn_id（见 §3）
5. 分支：
   ├─ regenerate=true：不新增 user，替换最后一条 AIMessage；
   │   assistant 版本 = 该 turn 现有 max(version)+1；conversation_log 只追加 assistant 条目
   └─ 正常：追加 [HumanMessage(query), AIMessage(summary_line)]；
       conversation_log 追加 user + assistant 两条（version=1）
6. trim_messages：按 max_tokens 截断 messages（保留最近窗口）
7. 被挤出的旧消息 → _merge_memory_summary 折叠进 memory_summary（带长度上限）
8. 落库：get_conversation_message_repo().append_messages(thread_id, entries)
   —— 在返回 state 之前写，写失败则抛错、checkpoint 不前移
9. 返回 state：messages（RemoveMessage(ALL) + trimmed）、memory_summary、conversation_log
```

关键点：

- **`messages` 用 `RemoveMessage(REMOVE_ALL_MESSAGES) + trimmed_messages` 整体替换**，避免 `add_messages` 累积导致上下文无限膨胀（[memory.py:221](../ai_hunter/app/graph/nodes/memory.py#L221)）。
- **`content = full_answer`** 是报告全文进入历史表的入口；脱水 `summary_line` 只进 `messages`（喂 LLM）。两套数据分流于此。
- **重新生成（regenerate）**：同一 `turn_id` 下 assistant 多版本累积，`version` 递增，前端可按版本切换（见 `/turns` 接口）。

## 5. 读取链路

### 5.1 入图前：`hydrate_memory_context`

主图第二个节点（[memory.py:56-79](../ai_hunter/app/graph/nodes/memory.py#L56)）。把「滚动摘要 + 最近窗口」拼成 `memory_context` 注入下游：

```
recent = trim_messages(messages, max_tokens=langgraph_memory_max_tokens,
                       strategy="last", start_on="human")
memory_context = "[历史摘要]\n{memory_summary}\n\n[最近对话]\n{recent}"
```

### 5.2 历史查询：`ConversationService`

[services/conversation_service.py](../ai_hunter/app/services/conversation_service.py)，单例（lru_cache）。

- `get_thread_messages`（[L243](../ai_hunter/app/services/conversation_service.py#L243)）：**优先**读 `conversation_messages`（快路径）；空则**回退**到 checkpointer 反序列化（`conversation_log` → 再退 `messages`），兼容统一表出现之前的 legacy 线程。
- `list_threads` / `get_thread_detail`（[L50](../ai_hunter/app/services/conversation_service.py#L50) / [L162](../ai_hunter/app/services/conversation_service.py#L162)）：从 `checkpoints` 表的 `channel_values` 抽取线程元信息（case_id / 最后 query / intent / final_report_ref / 时间戳），并生成标题。仅取 `deleted_at IS NULL` 的最新 checkpoint。
- `delete_thread`（[L389](../ai_hunter/app/services/conversation_service.py#L389)）：软删 `checkpoints.deleted_at`，并 best-effort 软删 `conversation_messages`。
- `_is_thread_deleted`（[L336](../ai_hunter/app/services/conversation_service.py#L336)）：checkpoint 或 conversation_messages **任一存活**即视为线程存活——保证「只写了新表、还没 checkpoint」的线程也可查询。

### 5.3 轮次聚合：`get_turns`

[conversation_message_repo.py:223-282](../ai_hunter/app/repositories/conversation_message_repo.py#L223)：把消息按 `turn_id` 前缀（剥掉 `_user`/`_assistant`）分组为「1 条 user + N 条 assistant（按 version 升序）」，供前端按轮渲染、支持 regenerate 多版本切换。

## 6. 双 checkpointer：同步 vs 异步

[graph/checkpointer.py](../ai_hunter/app/graph/checkpointer.py) 维护**两套**不可互换的 saver：

| 路径 | saver | 触发 | 说明 |
|---|---|---|---|
| 非流式 JSON | `PostgresSaver`（同步，连接池，lru 单例） | `/chat/invoke` 无 stream | `graph.stream` 跑在线程池里 |
| SSE 流式 | `AsyncPostgresSaver`（异步，连接池，双检锁单例） | `/chat/invoke?stream=true` | `astream_events` 需要 `aget_tuple`，同步 saver 没有 |

- 两者**读写同一张 `checkpoints` 表**，靠 thread 级 advisory lock 串行化。
- `LANGGRAPH_CHECKPOINTER=memory` 或 Postgres 不可达 → 回退 `MemorySaver`（**测试通过不代表持久化生效**）。
- `settings.postgres_checkpointer_dsn` 会去掉 DSN 里的 `+psycopg` 后缀再交给 LangGraph。
- 异步池由 FastAPI lifespan `close_async_checkpointer` 优雅关闭。

## 7. 并发、顺序与幂等

三道防线，保证多 worker、重复提交、重试场景下的一致性：

1. **thread 级串行**：`thread_advisory_lock(dsn, thread_id)`（[pg_lock.py:21](../ai_hunter/app/utils/pg_lock.py#L21)）。PostgreSQL advisory lock 跨进程生效（多 uvicorn worker 也序列化同一线程的执行）。非流式路径在 `invoke_chat` 里持锁跑图（[routes_chat.py:289](../ai_hunter/app/api/routes_chat.py#L289)）。
2. **客户端幂等缓存**：`_resolve_cached_turn(thread_id, client_turn_id)`（[routes_chat.py:88](../ai_hunter/app/api/routes_chat.py#L88)）。命中 `{turn_id}_assistant` 已存在则直接返回旧答复，不重复跑图（`regenerate=true` 时绕过）。流式路径有对应的 `_cached_sse_response`。
3. **落库幂等**：`append_messages` 用 `ON CONFLICT DO NOTHING`；user 唯一索引兜底；`conversation_log` reducer 按 `id` 去重。

## 8. 记忆策略与相关配置

| 配置（[settings.py:49-51](../ai_hunter/app/settings.py#L49)） | 默认 | 含义 |
|---|---|---|
| `langgraph_memory_window` | 12 | 最近对话窗口条数（语义参考） |
| `langgraph_memory_max_tokens` | 1200 | `trim_messages` 截断阈值（近似 token 计） |
| `langgraph_memory_summary_chars` | 1200 | 滚动摘要 `memory_summary` 的字符上限 |

记忆 = **滚动摘要（旧）+ 最近窗口（新）**：

- 每轮 `persist` 时，超出窗口被 trim 掉的旧消息，折叠进 `memory_summary`（`_merge_memory_summary`，超上限则保留尾部）。
- 入图时 `hydrate` 把 `memory_summary + 最近窗口` 拼成 `memory_context`。
- 长报告不进 messages，因此摘要不会被报告正文撑爆。

## 10. 两条执行路径的持久化收尾

```
非流式（/chat/invoke）：
  advisory_lock → 幂等缓存命中? →（否）_run_graph_with_logging(graph.stream)
    → finalize_answer → persist_conversation_memory（落库）
    → _capture_recovery_after_turn（回款自动捕获，best-effort）
    → _build_final_response（JSON）

流式（/chat/invoke?stream=true）：
  幂等缓存命中? →（否）astream_events 边出边发 SSE
    （section_start/section_chunk/section_reasoning_chunk/section_done + text_chunk/reasoning_chunk）
    → 图内 persist_conversation_memory 已落库
    → aget_state(config) 取完整终态（补回 trace_items/citation_coverage 等只在 checkpoint 里的字段）
    → _capture_recovery_after_turn → SSE final + done
```

> 流式结束后用 `aget_state` 回捞终态，是因为 `astream_events` 的增量 chunk 不含只存在于 checkpoint 的聚合字段（[routes_chat.py:424-426](../ai_hunter/app/api/routes_chat.py#L424)）。

## 11. 已知约束与陷阱

- **同步/异步 checkpointer 不可互换**：流式必须用 async saver；写代码切路径时注意。
- **MemorySaver 回退是静默的**：Postgres 不可达会回退内存，单测能过但重启即丢历史；联调持久化前先确认连上 Postgres。
- **legacy 线程回退有成本**：老线程没有 `conversation_messages` 行，`get_thread_messages` 会反序列化 checkpoint，相对慢；新线程都走快表。
- **DDL 需手动执行**：`conversation_messages.sql`、`add_soft_delete_to_checkpoints.sql` 等首次启动前要跑（除非 `LANGGRAPH_CHECKPOINTER_AUTO_SETUP=true` 且仅覆盖 checkpointer 自带表）。
- **复盘/审计报告共用持久化链路**：复盘报告（intent=review）同样落 `conversation_messages.content` + `final_report_ref`，靠 `intent` 区分，无需独立存储。
- **`clean_duplicate_conversation_log.sql` 是物理删除**：仅供测试重置线程，生产用软删。
- **drilldown agent 只「读」messages、不「写」主图 messages**：`run_drilldown_agent` 在 agent 运行前用 `_inject_current_query` 把当轮 `query` 注入 messages，但那只是**喂给 ReAct agent 的输入视图**（`create_react_agent` 的 callable-prompt 不会自动补 `state["messages"]`，必须手工拼）。节点最终只返回 `agent_output`，主图 `messages` 仍由 `persist_conversation_memory` 统一写——避免与单写者重复落库。regenerate 时若当轮 query 已是最近 Human，则截断其后旧 AI 回答而非重复追加。

## 12. 一图总览

```
                       POST /chat/invoke
                              │
                  advisory_lock(thread_id)   ← 跨进程串行
                              │
              _resolve_cached_turn(client_turn_id)
                   命中 ┌────┴────┐ 未命中
              直接返回 │          │  跑主图（sync graph.stream / async astream_events）
                       │          │            │
                       │          │   hydrate_memory_context（读 memory_summary + messages 窗口）
                       │          │            │  …业务节点…
                       │          │   finalize_answer
                       │          │            │
                       │          │   persist_conversation_memory：
                       │          │     ├─ 脱水 summary_line → messages（喂 LLM，整体替换）
                       │          │     ├─ trim 溢出 → memory_summary（滚动摘要）
                       │          │     └─ append_messages → conversation_messages（全文 + 角标快照）
                       │          │
                       └────►  返回 / SSE
                                   │
   GET /chat/threads(/{id})(/messages)(/turns)
        └─ ConversationService / Repo 读 conversation_messages（快） or checkpoints（回退/元信息）
```
```
checkpoints（状态/续跑/元信息）  ←软删→  deleted_at
conversation_messages（历史全文/角标/版本）  ←软删→  deleted_at
heavy_payload_store（报告正文，三层）  ←ref→  final_report_ref
```
