# 设计方案 07 · 权限网关 v2 与多租户落地

> 状态：v2-A 私有化用户 / 公司 / 角色 / 本地登录 / 报告段落权限已完成并已同步真实库；v2-A.1 现有接口身份与模块权限接线已完成；v2-B 案件隔离、v2-C RLS、v2-D license、v2-E 平台用户中心仍待实施。
> 关联：`docs/design/06-权限网关与人员标签.md` v2 章、`docs/ROADMAP.md` Tier 3。

## 1. 背景

当前权限网关 v1 已实现：

- 认证信任用户中心 JWT / 开发头 / `AUTH_ENABLED=false` 放行。
- 授权由本项目维护角色到 audience / module 的映射。
- 人员标签、`/me`、`/roles`、报告段落过滤和模块级 403 已接入。

但 v1 仍有几个边界问题：

- JWT 中读取 `roles`，与“角色归本项目自管”的最终边界不一致。
- 只有段落和模块分权，没有公司级硬隔离。
- 案件、会话、用户列表尚未统一绑定 `company_id` / `owner_id` / `case_member`。
- 私有化部署 license key 还没有落地。

## 2. 目标

1. 支持两种身份来源：平台集成模式走用户中心，私有化模式走本项目本地用户管理。
2. 建立公司级硬隔离：不同公司互不可见。
3. 建立公司内案件可见性：公司管理员（`company_admin`）看本公司全部，普通成员看自己 owner / 参与的案件。
4. 将 v1 的 audience / module 分权保留，并叠加到多租户可见性之后。
5. 为私有化部署预留 license key 校验能力。

## 3. 非目标

- 平台集成模式下，不在本项目实现登录、注册、发 JWT，也不替代用户中心。
- 私有化模式下，需要本项目提供本地账号、角色、权限的自主管理能力。
- 不一次性重构所有业务表；优先以 case / thread 作为隔离锚点。
- 不在方案确认前执行任何数据库变更或数据回填。

## 4. 核心边界

### 4.1 部署身份模式

新增部署开关：

```env
AUTH_IDENTITY_MODE=private  # private | platform
```

两种模式职责不同：

| 模式 | 适用场景 | 用户来源 | 认证方式 | 角色 / 权限来源 | 公司来源 |
|---|---|---|---|---|---|
| `platform` | 集成平台 / SaaS / 统一用户中心 | 用户中心 | 用户中心 JWT | 本项目本地角色、权限映射 | JWT `company` claim |
| `private` | 私有化独立部署 / 客户自有环境 | 本项目本地用户表 | 本项目本地登录或本地管理员创建账号 | 本项目本地角色、权限映射 | 本项目本地公司 / 机构表 |

设计原则：

- 当前阶段先走 `private` 模式，原因是统一用户中心尚未搭建完成，若等待平台集成会阻塞项目进度。
- `platform` 模式下，本项目只验签 JWT，不做注册、登录、发 token。
- `private` 模式下，本项目需要自主管理用户、角色、权限和公司 / 机构归属；可选对接客户自有用户中心，但不能强依赖统一平台用户中心。
- 两种模式共用后续授权模型：`app_user`、`app_user_role`、`app_role_permission`、`app_report_section`、`app_role_report_section`、`case_member`、报告段落 / module 权限。
- `AUTH_IDENTITY_MODE` 只决定“用户是谁、公司从哪里来、如何登录”；不改变“本项目角色和权限由本项目维护”的边界。

阶段决策：

- **先实现 `private`**：本项目自主管理用户、公司 / 机构、角色、权限、登录态。
- **预留 `platform`**：配置、字段和适配器边界先留好；用户中心完成后再接 JWT `company/apps`。
- `platform` 接入时不推翻本地角色权限模型，只替换“身份和公司来源”。

### 4.2 平台模式边界

| 模块 | 职责 |
|---|---|
| 用户中心 | 用户身份、公司归属、可进入哪些产品、JWT 签发 |
| 不良资产项目 | 本项目角色、角色权限、人员标签、案件成员、公司内数据可见性 |

JWT v2 推荐 claims：

| claim | 含义 | 默认字段名 | 可配置 |
|---|---|---|---|
| user id | 用户唯一标识 | `sub` | `AUTH_JWT_USER_CLAIM` |
| name | 用户名 / 展示名 | `name` | `AUTH_JWT_NAME_CLAIM` |
| company | 所属公司 id | `company` | 新增 `AUTH_JWT_COMPANY_CLAIM` |
| apps | 可访问产品码列表 | `apps` | 新增 `AUTH_JWT_APPS_CLAIM` |

v2 后不再信任 JWT `roles` 作为项目角色来源。过渡期可保留开发头 / v1 roles 兼容开关，但生产路径以本地角色表为准。

### 4.3 私有化模式边界

私有化模式下没有强制用户中心前置，本项目需要补齐本地用户管理：

| 能力 | 私有化要求 |
|---|---|
| 本地用户 | 支持创建、禁用、更新用户；用户名 / 手机 / 邮箱等登录标识待确认 |
| 本地认证 | v2-A 采用账号密码登录 + 本项目短期 JWT；refresh token / 客户 SSO 后置 |
| 本地公司 / 机构 | 支持维护公司 / 机构，并绑定用户归属 |
| 本地角色 | 继续使用 `app_user_role` 管理项目角色 |
| 本地权限 | 继续使用 `app_role_permission` 管理 role → modules，并使用 `app_report_section` / `app_role_report_section` 管理 role → 审计报告段落 |
| License | 私有化模式建议默认启用 license 校验 |

私有化模式不应依赖 JWT `company/apps`；但如果客户提供自有用户中心，可通过适配器把外部身份同步 / 映射到本地 `app_user` 与 `company_id`。

## 5. 推荐数据模型

> 涉及新增表、改表列，后续 DDL 必须写入 `sql/`，并为每张表和每个新增/修改列补 `COMMENT`。

### 5.1 新增 / 调整表

#### `app_user_role`

用途：本项目用户到角色的多对多关系。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `user_id` | TEXT | 用户中心用户 id |
| `role_code` | TEXT | 本项目英文稳定角色码，关联 `app_role_permission.role_code` |
| `company_id` | TEXT | 角色所属公司；为空仅允许内部超级管理员类角色 |
| `assigned_by` | TEXT | 分配人用户 id |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 更新时间 |

约束建议：

- `UNIQUE(company_id, user_id, role_code)`。
- 普通角色必须有 `company_id`。
- 内部 `super_admin` 可以 `company_id=''`，但必须审计。

`role_code` 只能使用英文小写字母、数字和下划线，并且必须以字母开头；中文名称不得写入 `role_code`，只能写入 `app_role_permission.role_name`。

| role_code | role_name | 说明 |
|---|---|---|
| `super_admin` | 全局超级管理员 | 跨公司运维 / 初始化账号 |
| `company_admin` | 公司管理员 | 仅限本公司全权 |
| `project_manager` | 项目经理 | 项目负责人 |
| `investment_specialist` | 投资专员 | 投资决策 |
| `legal_specialist` | 法务专员 | 法务审查 |
| `finance_specialist` | 财审专员 | 财务审计 |
| `due_diligence_specialist` | 尽调专员 | 尽职调查 |
| `lawyer` | 律所律师 | 外部律师 |
| `project_assistant` | 项目助理 | 项目协助 |
| `legal_assistant` | 法辅专员 | 法务辅助 |

兼容策略：代码层会把旧中文角色码和旧 `__admin__` 规范化为英文 code；数据库层迁移见 `sql/auth_role_code_standardization.sql`。

#### `case_member`

用途：案件多人参与关系，普通成员可见 owner 案件和参与案件。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `case_id` | BIGINT | 案件 id |
| `company_id` | TEXT | 公司 id，用于硬隔离 |
| `user_id` | TEXT | 成员用户 id |
| `member_role` | TEXT | 案件内角色，可为空或复用项目角色 |
| `added_by` | TEXT | 添加人用户 id |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 更新时间 |

约束建议：

- `UNIQUE(case_id, user_id)`。
- `company_id` 与案件 `company_id` 必须一致。

#### `license_state` 或本地 license 配置表

用途：私有化部署激活状态记录。是否落库待确认，也可仅走 env / 文件。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `license_id` | TEXT | license 标识 |
| `company_id` | TEXT | 授权公司 |
| `payload` | JSONB | license 明文载荷 |
| `status` | TEXT | active / expired / revoked / invalid |
| `checked_at` | TIMESTAMPTZ | 最近校验时间 |

#### 私有化本地用户相关表

DDL 已落到 `sql/auth_v2_private_tables.sql`，并已按授权执行到真实库。

| 表 | 用途 |

| `local_user_credential` | 本地登录凭证，保存密码哈希 / MFA 状态 / 最近登录时间等 |

如果采用客户自有 SSO，则 `local_user_credential` 可以不落地，改为保存外部身份映射关系。

#### 审计报告段落权限相关表

| 表 | 用途 |
|---|---|
| `app_report_section` | 审计报告 8 段目录，使用稳定 `section_code` + `section_id` + `title`，供前端配置和后端过滤 |
| `app_role_report_section` | 角色 → 审计报告段落授权矩阵，支持前端配置每个角色可见的报告段落 |

#### `company_id` 生成与反查规则

已确认规则：

- `company_id` 不承载展示语义，不从 id 文本解析公司名称。
- 展示公司名称统一通过 `app_company.company_id -> app_company.company_name` 反查。
- `app_company.company_name_norm` 建唯一约束，保证同一标准化公司名唯一。
- 当前存量公司：
  - `company_name`: `国金中恒企业管理(海南)有限公司`
  - `company_id`: `co_f1824b82e2116701`
- `company_id` 生成方式：`co_` + `sha256(标准化公司全称)` 前 16 位 hex。

该规则的好处是 `company_id` 稳定、可重复生成、适合 URL/JWT/日志/接口传递；公司展示名可通过目录表唯一反查，也允许后续展示名调整。

### 5.2 需要改列的既有表

#### `app_user`

现有 `company` 为人员画像文本，v2 需要区分：

- `company_id`：用户中心公司 id，用于隔离。
- `company_name` 或继续保留 `company`：展示/人员画像。

建议不要直接复用 `company` 做隔离字段，避免“公司名称变化 / 同名公司 / 手填文本”污染权限边界。

#### `cases`

建议新增：

- `company_id`：案件所属公司。
- `owner_id`：案件 owner / 创建人。

当前已确认 NpaDemo 与 ai_hunter 共用同一个真实数据库，且两个服务均由当前团队维护。因此 v2-B 不再把下游本地 `case_acl` 投影作为主路线，而是升级共享 `public.cases` 契约：

- `cases.company_id`：案件所属公司 / 机构 id，用于公司硬隔离。
- `cases.owner_id`：案件 owner / 负责人。
- `cases.created_by`：案件创建人。

NpaDemo 作为上游工具层，需要在案件列表 / 详情 / 创建接口中理解这些字段；ai_hunter 作为下游编排层，在调用上游前仍先做 `require_case_access` 校验。

#### `conversation_messages` / thread 元信息

建议新增或补充：

- `company_id`：会话所属公司。
- `created_by`：会话创建人。

如果当前只有 message 表，没有 thread 元信息表，建议新增轻量 thread metadata 表，而不是在每条消息上重复做唯一判断。

## 6. 鉴权流程

请求进入后顺序：

1. `get_current_identity_v2`
   - `AUTH_IDENTITY_MODE=platform`：验 JWT，解析 `user_id`、`name`、`company_id`、`apps`；若 `AUTH_REQUIRE_PROJECT_ACCESS=true`，校验 `apps` 包含 `AUTH_PROJECT_CODE`；自动 upsert `app_user` 投影。
   - `AUTH_IDENTITY_MODE=private`：走本项目本地登录 JWT；解析 `user_id`、`name`、`company_id`；不校验 `apps`。
   - 两种模式最终都加载本地 `app_user_role`。
2. 租户可见性
   - 内部超级管理员：跨公司。
   - 公司管理员（`company_admin`）：本公司全部。
   - 普通成员：本公司 + owner / case_member。
3. 模块权限
   - 沿用 `require_module(name)`。
4. 报告段落权限
   - 以 `section_code` 精确过滤为主；`audience` 保留为兼容和迁移兜底。

顺序必须是：

`公司硬墙 -> case/thread 可见性 -> module 权限 -> section_code 段落过滤`

## 8. RLS 与上下文污染防护

推荐多层防护：

1. 应用层统一过滤，便于测试、可读性和服务间复用。
2. 业务连接在事务内注入租户上下文，避免连接池复用串租户。
3. Postgres RLS 兜底，避免漏接接口越权。
4. checkpointer、后台任务、超级管理员通道单独设计，不与普通业务连接混用。

### 8.1 应用层

新增 `ai_hunter/app/auth/tenancy.py`：

- `can_access_case(identity, case_id)`
- `visible_case_filter(identity)`
- `require_case_access(case_id)`
- `stamp_tenant_fields(payload, identity)`

所有 Repository / Service 的 case / thread 列表和详情查询必须显式调用租户过滤入口。RLS 是兜底，不替代应用层过滤。

### 8.2 连接池与 engine 分离

为避免上下文污染，建议按用途拆分连接 / engine：

| engine | 用途 | RLS 策略 | 备注 |
|---|---|---|---|
| `business_engine` | 普通业务查询与写入 | 最终启用严格 RLS | 请求路径默认只使用它 |
| `checkpointer_engine` | LangGraph checkpointer | 不直接套普通业务 RLS；通过 thread metadata 控制读取入口 | sync / async checkpointer 都要独立处理 |
| `admin_engine` | 迁移、运维、超级管理员后台 | 仅限受控后台 / 迁移脚本 | 不进入普通请求依赖，必须审计 |

注意：

- `admin_engine` 不是普通请求的“绕过开关”，只能用于迁移、维护、超级管理员后台，并记录审计日志。
- checkpointer 不能只依赖 `thread_id` 作为安全边界；`thread_id` 是技术隔离，不是权限隔离。

### 8.3 事务级租户上下文

业务连接使用事务级上下文变量，不使用普通 `SET`。推荐通过 `set_config(..., true)` 注入：

```sql
SELECT set_config('app.current_company', :company_id, true);
SELECT set_config('app.current_user', :user_id, true);
SELECT set_config('app.is_company_admin', :is_company_admin, true);
SELECT set_config('app.is_super_admin', :is_super_admin, true);
```

第三个参数 `true` 表示 local/事务级，事务结束自动失效。RLS policy 使用：

```sql
current_setting('app.current_company', true)
```

这样变量不存在时返回 `NULL`，不会因为缺变量直接抛错。

不建议把普通 `SET` + `RESET` 作为主要安全机制：

- 连接池复用时普通 `SET` 可能污染下一次请求。
- 异常事务中 `RESET` 可能失败。
- `RESET` 可以作为双保险，但不能依赖它保证安全。

建议后续实现一个统一的 `tenant_context(session, identity)` 或 DB session dependency，所有业务查询必须在该上下文内执行。

### 8.4 FastAPI / LangGraph 生命周期

- FastAPI middleware 可以解析 identity，但不能保证所有 DB 连接都已注入租户变量。
- 真正的 tenant context 应落在统一 DB session dependency / repository 入口。
- LangGraph 节点若访问业务库，必须显式获得带租户上下文的 business session。
- SSE 流式请求跨异步图执行时，identity / company_id 必须进入 graph config 或 state 中，用于后续节点校验。

### 8.5 Checkpointer 策略

checkpointer 建议使用独立 engine，不直接套普通业务 RLS。原因：

- LangGraph checkpointer 有 sync / async 两套实现。
- checkpointer 连接池复用和事务边界与业务请求不同。
- checkpointer 数据本身按 `thread_id` 组织，不天然知道公司和用户。

但 checkpointer 不能无约束暴露。必须新增或维护 thread metadata：

| 字段 | 说明 |
|---|---|
| `thread_id` | LangGraph thread id |
| `company_id` | 线程所属公司 |
| `created_by` | 创建人 |
| `case_id` | 关联案件，可空 |
| `created_at` / `updated_at` | 时间戳 |

所有 `/threads`、`/threads/{id}`、`/threads/{id}/messages`、历史回放和恢复入口先查 thread metadata，确认 company / user / case_member 可见后，才允许读取 checkpointer 或 conversation message。

### 8.6 RLS

RLS 设计需要单独评审，原因：

- LangGraph checkpointer 有 sync / async 两套连接。
- 连接池复用时必须保证 session 变量被正确设置和清理。
- 测试环境和 `AUTH_ENABLED=false` 需要有明确 bypass 方案。

建议先做应用层过滤、thread metadata、tenant context 基础设施和字段落库，RLS 放到 v2-C 启用。

RLS policy 示例思路：

```sql
company_id = current_setting('app.current_company', true)
AND (
  current_setting('app.is_super_admin', true) = '1'
  OR current_setting('app.is_company_admin', true) = '1'
  OR owner_id = current_setting('app.current_user', true)
  OR EXISTS (
    SELECT 1 FROM case_member cm
    WHERE cm.case_id = cases.id
      AND cm.user_id = current_setting('app.current_user', true)
  )
)
```

具体 SQL 以后单独写到 `sql/`，并按规范补齐表 / 列 comment。

### 8.7 监控与审计

记录以下安全事件：

- 请求 identity 缺失但访问受保护接口。
- company mismatch。
- case/thread 越权访问。
- RLS policy 拒绝。
- admin_engine 使用。
- 角色、权限、case_member、license 变更。

日志只记录必要字段：`request_id`、`user_id`、`company_id`、`case_id`、`thread_id`、action、decision，不记录敏感正文。

- 用户中心用户首次进入时 upsert `app_user` 投影。
- 保持本项目本地角色、权限、case_member 不变。

验收：

- JWT 不带 roles 时，仍可从本地角色得到权限。
- `AUTH_REQUIRE_PROJECT_ACCESS=true` 且 apps 不含项目码时返回 403。
- `AUTH_IDENTITY_MODE=platform` 时本地登录接口默认不可用，避免双身份入口混用。

## 13. 需要用户确认

1. 私有化本地登录已采用账号密码 + 短期 JWT；后续是否补 refresh token / 客户自有 SSO 适配仍待确认。
2. 私有化模式下公司 / 机构是单公司部署还是多公司部署。
3. 存量数据策略已确认采用默认公司 `国金中恒企业管理(海南)有限公司`；后续如出现多客户存量数据需重新评审。
4. `public.cases.company_id/owner_id/created_by` 已确认为案件权限权威字段并由两端接入；后续需完成所有案件路由的强制校验。
5. 公司管理员是否允许查看本公司全部会话历史。
6. License key 是否必须本期落地，还是 v2-D 后置。
7. 平台模式后续 JWT 中公司字段名是否确定为 `company`，产品准入字段名是否确定为 `apps`。
8. 平台模式后续本项目产品码是否使用 `npa`、`ai_hunter`，还是其它值。
9. checkpointer 是否只走 thread metadata 权限入口，还是也需要单独 RLS。
10. admin_engine 的可用范围和审计字段是否按本方案执行。

## 14. 风险

- 如果先做资产包拆分再做多租户，后续需要二次补权限边界。
- 如果直接启用 RLS 但未处理存量 `company_id IS NULL`，旧数据会被全部挡掉。
- 如果继续信任 JWT roles，未来平台多产品角色会混淆。
- 如果没有统一 `require_case_access`，接口容易出现个别漏过滤。
- 如果私有化仍强依赖用户中心，客户离线 / 内网部署会无法独立运行。
- 如果平台模式同时开放本地登录，会出现双身份入口和审计口径混乱。
- 如果使用普通 `SET` 而不是事务级 `set_config(..., true)`，连接池复用可能导致租户上下文污染。
- 如果 checkpointer 只依赖 `thread_id`，缺少 thread metadata 校验时仍可能越权读取历史。
- 如果 `company_id` 空值在私有化普通用户路径放行，会直接破坏公司硬隔离前提。
- 如果超级管理员操作没有强制审计，后续无法追溯跨公司访问和权限变更来源。

## 15. 建议结论

当前 v2-A 私有化闭环已完成，后续按数据隔离优先推进：

1. v2-A ✅ 已完成：`private` 模式最小闭环，本地用户、本地公司 / 机构、本地角色权限、本地登录态、审计报告段落权限矩阵。
2. v2-B ✅ 已完成：共享 DDL、NpaDemo 案件租户/成员接口、ai_hunter tenancy 服务、thread metadata、案件路由强制校验及存量 159 个 thread 安全迁移均已完成。
3. RLS 和 license key 后置到 v2-C / v2-D，避免一次性把身份、数据、连接池和私有化激活风险叠加。
4. v2-E 再接平台用户中心；平台模式只替换身份 / 公司来源，不推翻本地角色权限模型。
