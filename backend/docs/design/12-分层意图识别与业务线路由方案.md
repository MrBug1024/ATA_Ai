# 分层意图识别与业务线路由方案

> 状态：Phase 1-2、Phase 2.5.0-2.5.3 已完成实现；Phase 2.5.4 已完成写命令迁移、隔离真实写入验收和生产 legacy 模式部署，`business_line` 切流与观察窗口待执行；Phase 3 持续迭代
> 日期：2026-07-19
> 适用范围：`POST /chat/invoke` 顶层 LangGraph 路由、下钻 Agent 工具选择及路由审计

## 1. 背景

当前顶层仅使用 `full_audit / re_audit / review / drilldown` 四类意图。完整审计、修正重审和回款复盘有独立分支，但案件创建、材料处理、任务督办、证据追溯、知识图谱、企业穿透、时效查询等能力都被压入 `drilldown`，再由同一个 Agent 从全部工具中临场选择。

这种设计存在三个问题：

1. 顶层意图正确不等于业务线正确，`drilldown` 内仍可能选错工具。
2. 关键词规则存在覆盖冲突，例如“查一下估值错误并重审”可能被“查一下”提前截获。
3. 路由只保存最终字符串，没有业务线、具体能力、置信度、判定来源和澄清状态，难以评估和回放。

### 1.1 当前实现边界

Phase 1-2 已完成分层分类、能力级权限和工具收敛；Phase 2.5.0-2.5.4 已落地单一注册表、四个业务线子图、七个确定性只读节点、三个专用图入口、两个领域 Agent 和三个确定性写命令节点。当前执行层由配置决定：

```text
ROUTER_EXECUTION_MODE=legacy
  -> 继续按 full_audit / re_audit / review / drilldown 执行

ROUTER_EXECUTION_MODE=business_line
  -> 已迁移 capability 进入对应业务线子图
  -> case.create / material.upload / task.write 进入确定性写命令节点
  -> needs_clarification=true 始终进入 clarify_route
```

`intent` 继续保留为外部和历史兼容字段，但在 business-line 模式下不再决定已迁移 capability 的执行边。审计下钻和图谱查询已分别使用独立 prompt 与固定工具集；旧顶层报告字段仍保留兼容，同时新增业务线轻量 context 投影。

## 2. 目标

1. 先识别业务线，再识别具体能力；迁移期保持旧意图兼容，最终由业务线子图承担执行。
2. 高置信强信号由确定性规则处理，复杂语义由结构化 LLM 处理。
3. 低置信度或缺少写操作目标时进入澄清分支，不默认交给万能 Agent。
4. 下钻 Agent 只暴露当前 capability 所需的工具集合。
5. API、SSE、日志和会话状态可审计地保留路由决策。
6. 新增业务线时通过注册表和独立子图扩展，不持续膨胀顶层主图、统一 Agent 和公共 State。

## 3. 两级路由模型

### 3.1 一级：业务线

| business_line | 业务范围 |
|---|---|
| `operator` | 案件创建、材料上传、OCR、类别校验、补件、批次状态 |
| `audit_analysis` | 完整审计、修正重审、局部分析、证据追溯、知识图谱、企业和资金分析 |
| `supervision` | 任务查询/写入、司法时效、进度、回款复盘 |
| `common` | 闲聊、帮助、导航、无法稳定判断的请求 |

### 3.2 二级：能力

首期 capability：

- `case.create`、`case.profile`
- `material.upload`、`material.status`、`material.validate`
- `audit.full`、`audit.reaudit`、`audit.drilldown`
- `evidence.resolve`、`caselaw.search`、`graph.query`
- `task.query`、`task.write`
- `deadline.query`、`recovery.review`
- `common.general`、`clarify`

当前兼容映射：

- `audit.full -> full_audit`
- `audit.reaudit -> re_audit`
- `recovery.review -> review`
- 其余可执行能力暂映射为 `drilldown`
- `needs_clarification=true` 时由主图条件边进入 `clarify`，不调用业务工具

该映射仅是 Phase 1-2 迁移兼容层，不是最终执行架构。Phase 2.5 完成后，`intent` 继续作为 API / 历史数据兼容字段，但主图执行边应优先读取 `business_line`，业务线子图内部再按 `capability` 分流。

## 4. 路由决策契约

```json
{
  "business_line": "supervision",
  "capability": "task.write",
  "intent": "drilldown",
  "confidence": 0.94,
  "needs_clarification": false,
  "source": "rule",
  "case_id": 116,
  "action": "complete",
  "target_id": "28",
  "clarification_question": ""
}
```

约束：

1. `intent` 由 capability 确定性派生，不信任模型自由填写。
2. `confidence < 0.60` 必须澄清；`0.60 <= confidence < 0.85` 在缺少案件/页面上下文时澄清；`audit.full / audit.reaudit / recovery.review` 无论置信度多高，缺少有效案件上下文都必须澄清。
3. 完成、指派、删除、创建等写操作必须识别明确动作；需要对象 ID 的操作还必须识别目标。
4. 模型不可用、输出无法解析时安全降级到 `clarify`，不直接执行写操作。

## 5. 混合判定策略

判定优先级：

1. 请求结构强信号：附件、显式 case/task/batch ID、前端 workspace/active view。
2. 高精度规则：完整报告、明确重审、回款复盘、明确任务写动作等。
3. 结构化 LLM：复合问题、多轮指代、同义表达和规则未覆盖语义。
4. 置信度门槛与澄清。

规则不得继续扩展成无边界关键词字典；只保留能达到高精确率的硬信号。关键词冲突按“明确业务动作优先于泛查询词”处理。

## 6. 工具约束

按 capability 选择工具组：

| capability | 工具范围 |
|---|---|
| `case.*` | 案件创建/画像 |
| `material.*` | 文档类别、校验、解析、结构化入库 |
| `task.*` | 任务创建和管理 |
| `evidence.resolve` | 仅查询当前案件卷宗 claim、原文、页码和高亮锚点 |
| `caselaw.search` | 通过 CPWS/Qdrant 检索外部相似裁判案例；`case_binding=false`、`reference_only=true` |
| `graph.query` | 企业穿透、资金流、白手套和知识图谱查询 |
| `deadline.query` | 时效扫描 |
| `audit.drilldown` | 案件画像和四大审计引擎 |
| `common.general` | 不提供业务写工具 |

权限和案件租户门禁仍在工具/API 层执行；意图路由不能替代授权校验。

## 7. 可观测性与验收

路由日志至少包含：`route_version / business_line / capability / intent / confidence / source / needs_clarification`，不得记录模型隐藏推理。

测试语料需要覆盖：

- 单一意图、复合意图和冲突关键词。
- 首轮案件号、已有报告后的追问、多轮省略和指代。
- 否定句、错别字、口语、短句。
- 查询与写操作边界、缺少 task/case 目标。
- 模型不可用、非法结构化输出和低置信度。

首期验收指标：

- 业务线准确率不低于 97%。
- 写操作路由精确率不低于 99%。
- 低置信度请求澄清率 100%。
- 原有完整审计、重审、复盘和上传流程无回归。

## 8. 实施阶段

### Phase 1：兼容式结构化路由

- 新增 RouteDecision Schema 和状态字段。
- 统一 `prompts/router.txt` 为唯一模型提示词来源。
- 保留四意图主图执行分支，新增 `clarify` 分支。
- 修复关键词优先级和“只有案件号就完整审计”的误判。

### Phase 2：能力级工具收敛

- 建立 capability 到工具组的注册映射。
- 下钻 Agent 按 capability 只装载必要工具。
- API/SSE 返回 route decision，日志记录 route version。

### Phase 2.5：业务线执行子图与注册表驱动

目标：消除“多数 capability 最终仍进入通用 drilldown Agent”的执行折叠，使分类结果真正决定业务工作流。

实施内容：

1. ✅ 已建立业务线和 capability 注册表，作为归属、执行器、权限、读写属性和工具集的唯一来源。
2. 顶层主图从 `intent_edge` 迁移到 `business_line_edge`，接入 `operator / audit_analysis / supervision / common` 四个子图。
3. 每个业务线子图内部按 capability 进入确定性节点、命令节点或领域 Agent。
4. 把查询和写操作拆开；`task.query` 不再暴露可更新任务的多动作工具。
5. 公共状态与业务线状态分层，新增业务线不再向 `AuditGraphState` 顶层持续堆字段。
6. 使用 Settings 配置 `ROUTER_EXECUTION_MODE=legacy|business_line`，支持灰度和无 DDL 回滚。

### Phase 3：数据驱动优化

- 建立真实匿名问句标注集和混淆矩阵。
- 新旧路由 shadow 对比后再调整阈值。
- 根据线上误判样本迭代 few-shot 示例和确定性规则。

## 9. Phase 2.5 目标执行架构

```text
START
  -> normalize_input
  -> hydrate_identity_and_context
  -> classify_route
       ├── needs_clarification -> clarify_route
       ├── operator            -> operator_subgraph
       ├── audit_analysis      -> audit_analysis_subgraph
       ├── supervision         -> supervision_subgraph
       └── common              -> common_subgraph
  -> finalize_answer
  -> persist_conversation_memory
  -> END
```

业务线内部执行：

```text
operator_subgraph
  ├── case.create       -> 参数校验 + 案件创建命令节点
  ├── case.profile      -> 案件画像确定性查询节点
  ├── material.upload   -> ingest_graph / 上传 API 衔接
  ├── material.status   -> 批次和材料状态确定性查询节点
  └── material.validate -> 类别完整度与缺件校验节点

audit_analysis_subgraph
  ├── audit.full        -> full_audit_graph
  ├── audit.reaudit     -> extract_correction -> full_audit_graph
  ├── audit.drilldown   -> 审计领域 Agent
  ├── evidence.resolve  -> 本案卷宗证据解析确定性节点
  ├── caselaw.search    -> 外部类案检索确定性节点
  └── graph.query       -> 图谱领域 Agent / 图谱查询节点

supervision_subgraph
  ├── task.query        -> 只读任务查询节点
  ├── task.write        -> 目标校验 + 任务命令节点
  ├── deadline.query    -> 时效确定性查询节点
  └── recovery.review   -> review_graph

common_subgraph
  ├── common.general    -> 无业务工具的通用回复节点
  └── clarify           -> clarify_route
```

### 9.1 节点选型原则

- 固定输入输出、可一次查询完成的能力优先使用确定性节点，不调用 Agent。
- 创建、更新、完成、指派等写操作使用命令节点，必须校验权限、目标和必要参数。
- 只有需要多步探索、动态选工具的 `audit.drilldown / graph.query` 使用领域 Agent。
- 路由只决定执行入口，权限和案件租户门禁仍必须在子图入口及具体 API / 工具层执行。

## 10. 注册表驱动的扩展模型

### 10.1 业务线注册表

```python
BUSINESS_LINE_REGISTRY = {
    "operator": BusinessLineSpec(
        graph_factory=build_operator_graph,
        capabilities={"case.create", "case.profile", "material.upload", "material.status", "material.validate"},
    ),
    "audit_analysis": BusinessLineSpec(
        graph_factory=build_audit_analysis_graph,
        capabilities={"audit.full", "audit.reaudit", "audit.drilldown", "evidence.resolve", "caselaw.search", "graph.query"},
    ),
    "supervision": BusinessLineSpec(
        graph_factory=build_supervision_graph,
        capabilities={"task.query", "task.write", "deadline.query", "recovery.review"},
    ),
    "common": BusinessLineSpec(
        graph_factory=build_common_graph,
        capabilities={"common.general", "clarify"},
    ),
}
```

### 10.2 capability 注册表

```python
CAPABILITY_REGISTRY = {
    "task.query": CapabilitySpec(
        business_line="supervision",
        executor="query_tasks",
        permission_module="progress",
        execution_mode="deterministic",
        write_operation=False,
    ),
    "task.write": CapabilitySpec(
        business_line="supervision",
        executor="write_task_command",
        permission_module="progress",
        execution_mode="command",
        write_operation=True,
        required_slots={"case_id", "action", "target_id"},
    ),
}
```

注册表必须成为以下信息的唯一权威来源：

- capability 属于哪条业务线。
- 使用哪个执行节点 / 子图。
- 需要哪个权限模块。
- 是只读、写操作还是 Agent 探索。
- 必填槽位、可用工具组和默认澄清问题。

`RouteDecisionModel` 不再手工维护多份 capability Literal；建议改为字符串字段 + 注册表 validator，路由提示词中的业务线和 capability 清单也由注册表生成，避免 Schema、提示词、权限表和工具表漂移。

### 10.3 新业务线扩展示例

新增“资产包筛选与投决”时：

```python
"investment": BusinessLineSpec(
    graph_factory=build_investment_graph,
    capabilities={
        "package.profile",
        "package.screen",
        "investment.evaluate",
        "investment.review",
    },

```

需要新增注册项、业务线子图、权限定义、提示示例和测试语料，但不修改现有四条业务线内部实现。LangGraph 在应用启动时根据注册表编译，新增业务线需要发布和重启，不承诺运行时热插拔。

## 11. 状态边界

共享状态只保留跨业务线字段：

```text
thread_id / user_id / query / messages
current_case_id / identity / route_decision
final_report / agent_output / errors
```

业务线专属状态进入命名空间：

```text
operator_context
audit_context
supervision_context
investment_context
```

实施时优先使用 TypedDict / Pydantic 子模型约束各命名空间。旧顶层字段迁移期保留只读兼容映射，待历史 checkpoint 兼容窗口结束后再单独评审清理，不能与 Phase 2.5 首次切换同时删除。

## 12. Phase 2.5 迁移顺序

### 2.5.0：注册表与一致性检查

- ✅ 新增 `BusinessLineSpec / CapabilitySpec` 和不可变注册表。
- ✅ Schema、路由提示目录、API 权限、工具集和 Agent 分支改为读取注册表。
- ✅ 新增 `ROUTER_EXECUTION_MODE=legacy|business_line` Settings 契约；本阶段主图仍固定使用 legacy 执行。
- ✅ 增加注册完整性测试：每个 capability 必须且只能属于一条业务线，并具备执行器和权限模块。
- ✅ 未知 capability 由 Schema 拒绝；损坏状态进入空工具安全兜底，不再默认获得审计下钻工具。

### 2.5.1：业务线子图骨架与 shadow

- ✅ 新增四个业务线子图骨架并编译，覆盖全部已注册 capability，但不接管生产执行。
- ✅ 在原 `classify_intent` 节点内同时计算 legacy 目标和 business-line 目标，只写 checkpoint 内部 `route_shadow` 和日志。
- ✅ 不新增主图节点，不改变 SSE 事件序列；`route_shadow` 不进入 JSON/SSE 响应。
- ✅ `active_mode` 固定为 `legacy`；写 capability 标记 `write_shadow_blocked=true`，shadow 不执行任何业务工具。

### 2.5.2：迁移只读能力

- ✅ 已迁移 `case.profile / material.status / material.validate / evidence.resolve / caselaw.search / task.query / deadline.query`。
- ✅ 七个 capability 使用注册表 `business_line_executor` 和确定性参数；未迁移能力继续 legacy。
- ✅ `evidence.resolve` 按 `case_id` 在案件 `kg_claim/kg_evidence_link/source_*` 中检索并最多返回 5 条卷宗证据；显式角标/claim 请求优先使用当前 `trace_items` 的稳定映射。`caselaw.search` 才调用 CPWS/Qdrant，并固定标记为外部参考。
- ✅ 统一返回 `agent_output + business_line_result`，最终 JSON/SSE 继续使用原 `final_report / route_decision` 契约。
- ✅ 缺案件号时不调用工具；`task.query` 固定 `action=list`；`material.validate` 只读取类别目录和案件缺件状态。
- ✅ JSON/SSE 模块权限在业务线节点执行前拒绝；新会话案件/租户门禁仍由 `ensure_thread_for_invoke` 在图启动前执行。
- ✅ `ROUTER_EXECUTION_MODE=legacy` 一键回滚全部只读路径，默认值保持 `legacy`。

### 2.5.3：迁移专用图和 Agent

- ✅ `audit.full` 接入现有 `full_audit_graph`；`recovery.review` 接入 `review_graph`。
- ✅ `audit.reaudit` 封装为 `extract_correction -> full_audit_graph`，不直接修补旧报告。
- ✅ `audit.drilldown / graph.query` 使用独立 prompt、固定 capability 和注册表约束工具集。
- ✅ 新增 `operator_context / audit_context / supervision_context / common_context` 轻量命名空间；旧顶层字段在 checkpoint 兼容窗口继续保留。
- ✅ `execution_route_edge` 在配置开启且 capability 已迁移时进入业务线子图；旧 intent 继续作为兼容字段。
- ✅ 完整审计从业务线子图返回后继续经过原 `should_create_tasks` 条件边，不丢失任务创建行为。
- ✅ 注册表通过 `requires_case` 声明案件型能力；规则路由和结构化模型路由在补齐 query/thread 上下文后统一校验，缺案件时进入 `clarify_route`，不执行报告、修正、进度或任务写入。

### 2.5.4：迁移写操作

#### 写命令契约

`POST /chat/invoke` 新增可选 `write_command` 结构化输入，与用户自然语言共同形成命令参数。结构化字段优先，自然语言只解析显式标签和高置信动作；任何必填槽位缺失都进入 `clarify_route`，不调用写 API。

| capability | 业务线 | 命令节点 | 必填槽位 | 幂等边界 |
|---|---|---|---|---|
| `case.create` | `operator` | `create_case_command` | `case_name` + `debtor_name` | 前端 `client_turn_id` 防止轮次重放；上游按公司 + 债务人/USCC 复用已有案件 |
| `material.upload` | `operator` | `record_material_upload_command` | 正数 `case_id` + `uploaded_files` | `upload_batch_id` + 文件 SHA256 去重；摄入图在顶层 pre-route 只执行一次，命令节点只验收结果，不二次摄入 |
| `task.write` | `supervision` | `write_task_command` | 正数 `case_id` + 明确动作；完成/更新/指派还需 `task_id` | 创建按 case + action 由上游去重；更新/指派为目标状态幂等写 |

#### 安全与租户边界

1. `identity_context` 只能由 FastAPI 鉴权依赖注入图输入，`ChatRequest` 不暴露该字段，调用方不能伪造 `company_id / owner_id / created_by`。
2. `case.create` 允许在未绑定案件的新会话中执行，但会话必须先绑定当前用户和公司；上游返回案件后立即回绑 `thread_metadata.case_id`。
3. 路由前用 query 中的显式案件号与请求 `current_case_id` 计算实际目标；已绑定案件 A 的会话不得通过 query 切换到案件 B 执行写命令。

## 14. 后期方案三：业务线独立 Agent

当业务线工具和流程继续增长时，可升级为“顶层业务线 Router + 业务线专属 Agent”。相较当前方案二，其长期优势是：

1. 每个 Agent 拥有独立提示词、状态和工具集，领域边界更清晰。
2. 不同业务线可独立选择模型、超时、并发和降级策略。
3. 新增业务线时不必持续扩张单一 capability 枚举和统一 Agent 提示词。
4. 可由业务线 Agent 完成更复杂的多步规划，而不只是单次工具选择。

暂不直接采用的原因：当前工具规模有限，多 Agent 会增加模型调用次数、延迟、成本、状态同步和调试复杂度。待单条业务线出现多个独立子流程、工具规模明显增长或需要不同模型策略时再评审升级。

## 15. 回滚点

Phase 2.5 上线保持旧 `intent` 字段和 legacy 执行分支。发生误路由或子图异常时，将 Settings 中 `ROUTER_EXECUTION_MODE` 切回 `legacy` 并重启服务，恢复现有 `intent_edge + drilldown_agent_graph`；不涉及 DDL，不修改存量会话数据。
