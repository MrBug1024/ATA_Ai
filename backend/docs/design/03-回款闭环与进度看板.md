# 设计方案 03 · 回款闭环与进度看板

> 路线图 Tier 1 第 3 项（见 [../ROADMAP.md](../ROADMAP.md) 决策四）。
> 状态：**Phase 1 已实现并合入**（数据模型 + 进度看板接口 + 预期种子化 + 催收/利润提醒）。Phase 2（AI 复盘 + 规则迭代）待后续。
> 已决策（2026-06-17）：3 表拆分；会议阶段枚举；AI 复盘放 Phase 2；提醒规则给默认值可配（`RECOVERY_OVERDUE_DAYS`/`PROFIT_DISTRIBUTION_THRESHOLD_PCT`）；新建 `routes_progress.py`；预期回款 reconcile 后自动种子化 + 接口可触发。
> 定位：项目核心 KPI 是「能拿回多少钱」。当前系统只到"出报告"，缺**回款/进度跟踪 → 归档 → AI 复盘 → 规则迭代**的闭环。

---

## 1. 现状（事实）
- 回款/进度**完全无数据基建**（仅出现在报告文案）。
- SOP 任务走统一后端中的 **task API**（`10.0.10.2:8081 /api/tasks/*`），非本地表。
- 有 `material_event` 表（上传事件边界：received/processing/completed/failed），与回款无关。
- 数值引擎已产出**预期回款**：`computed_metrics.npv.tranche_forecast`（T1/T2/T3）+ `recovery_rate` —— 可作"预期"种子。

## 2. 闭环全景
```
出全量报告(预期回款) → 执行(SOP任务) → 回款&进度跟踪 → 归档 → AI复盘(预期vs实际) → 经验→规则迭代
```
**分两期**（ROADMAP：先数据模型+看板，再 AI 复盘+规则迭代）：
- **Phase 1（本次）**：回款/进度**数据模型** + **进度看板读写接口** + 预期回款从报告种子化 + 催收/利润提醒（规则可配）。
- **Phase 2（后续）**：AI 复盘审计（预期 vs 实际对账，复用报告框架）+ 规则迭代学习回路。

## 4. Phase 1 接口（`routes_progress.py` 或并入 routes_files）
| 接口 | 方法 | 作用 |
|---|---|---|
| `/cases/{case_id}/progress` | GET | **进度看板聚合**：stage/status/风险提示/预期·实际回款汇总/时间线/催收·利润提醒 |
| `/cases/{case_id}/progress` | PUT | 更新阶段/状态/风险 |
| `/cases/{case_id}/recovery` | POST | 记一笔实际收款（写 recovery_record，刷新 actual_total） |
| `/cases/{case_id}/recovery` | GET | 收款明细列表 |
| `/cases/{case_id}/forecast` | POST/GET | 写/读预期回款（或从报告一键种子化） |

**催收/利润提醒**（看板聚合时按规则算，规则参数可配）：
- 催收：某预期回款 `expected_date` 已过且未达对应实收 → 标"待催收 N"。
- 利润分配：实收累计达预期的阈值 X%（默认待客户定）→ 标"可分配利润提醒"。

## 4.5 实收自动捕获（Tier1-3，已实现）
实收除手工 API 录入外，还从文本**保守自动抽取**（关键词预过滤 → LLM → 手动 JSON 解析，跨 provider 稳）：
- **触发点（3 条，归为 2 个集成点）**：
  1. 补卷材料（chat 带附件 ingest）→ 扫 `aggregated_text`；
  2. 对话描述（用户 query 里"某房产已回款/分红到账"）→ 扫 query；
  3. 操作员上传卷宗（`/files/upload-and-ingest`）→ 扫 `aggregated_text`。
  实现：chat 路径在 `routes_chat._capture_recovery_after_turn`（query + 本轮上传材料）；操作员路径在 `_run_upload_ingest_job`（材料）。
- **安全模型（核心 KPI 防污染）**：自动抽取的收款写 `status='pending'`、`origin=ingest_material/chat`，**不计入实收总额**；看板亮"待确认收款 N 笔"，人工经 `POST /cases/{id}/recovery/{rid}/confirm` 确认后才计入。手工 API 录入直接 `confirmed`。
- 抽取保守：只取"已实际发生"，忽略预期/计划/约/拟。

## 5. 集成点
- **预期种子化**：报告生成后（reconcile 之后或显式调用），把 `computed_metrics.npv.tranche_forecast` 写入 `recovery_forecast` + 回填 `case_progress.expected_recovery_total`、`report_ref`。
- **风险提示**：从报告 `computed_metrics.data_quality`（归零/盲估/缺卷）+ 时效看板红/过期项聚合进 `case_progress.risk_alerts`。
- **金额口径**：内部存元；看板展示用 `metrics_engine.format_amount`（报告万元 / 文书元）。

## 6. Phase 2

### Phase 2-A（已实现，2026-06-17）：AI 复盘审计
项目终结/阶段复盘时，取「预期回款(forecast/NPV) vs 实际回款(records，仅 confirmed)」做对账复盘报告，**复用八段式段子 agent 框架**（并行扇出 + 专家 persona + 有界并发 + 流式 + 容错），新增 `intent=review` + `review_graph` 子图。
- **确定性三视角对账**（`graph/review_metrics.py`，纯函数，LLM 只解读不算数）：
  - 总量：预期总额 vs 已确认实收 → 达成率/差异额/差异率；
  - 时点：按 forecast.expected_date 累计"截至今日应收 vs 已收" → 时点缺口（催收口径）；
  - 路径：实收按 disposal_path 分组展示（预期侧无路径分档则不强配对）。
- **复盘 3 段**（`review_sections.py`，id `R1/R2/R3`，prompt `review_s{1,2,3}.txt`）：对账总览 / 差异归因 / 经验与规则建议。
- **子图**（`subgraphs/review_graph.py`）：`fetch_review_context(拉数据+对账) → [3 段并行] → reconcile_review(拼接+去千分位)`。
- **触发**：① 对话 `intent=review`（关键词"复盘/对账/回款复盘…"，`routers.py`）；② 接口 `POST /cases/{id}/review`（`routes_review.py`，额外返回结构化对账指标）。
- **持久化**：复盘报告复用 `final_report_ref` 走 finalize→persist，全文 + ref 落 `conversation_messages`（`intent=review`），历史可取回、按 intent 区分。**只读对账**：不改 case_progress、不抽任务、不种子化。
- 金额一律万元/4位/无千分位。
- 测试：`tests/test_review_metrics.py` / `tests/test_review_graph.py` / `tests/test_routers.py`。真实 case 116 端到端已验证。
