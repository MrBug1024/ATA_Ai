# 案件参与方角色模型与债务人解析治理

## 1. 背景

案件 116 曾将资产购买方“中国中信金融资产管理股份有限公司”写入
`debtors.entity_name`，导致案件名、查控清单、关联人、审计缓存和下游上传上下文
都把购买方当成债务人。现有材料抽取还包含“受让/转让整体资产”规则，存在再次把
受让方识别为债务人的风险。

本方案建立正式案件参与方模型，并把债务人解析从“材料猜测优先”调整为“案件主数据
优先、冲突安全失败”。

## 2. 目标与范围

- 新增 `public.case_party`，统一表达案件参与方及其角色。
- 保留 `public.debtors` 作为债务人专项画像和现有业务外键的权威来源。
- 债务人参与方通过 `case_party.debtor_id` 与 `debtors` 精确关联。
- 支持 `debtor`、`asset_purchaser`、`creditor`、`guarantor`、
  `administrator`、`other` 六类角色。
- NpaDemo 建案时在同一事务中创建案件、债务人和债务人参与方。
- NpaDemo 案件画像和参与方接口返回结构化 `parties`。
- ai_hunter 上传时只从 `debtors` 解析债务人，不从全部参与方中猜测。
- 案件 116 显式登记晨光煤矿为债务人、中信金融资产为资产购买方。

不在本阶段处理：

- 不把卷宗中出现的所有债权人自动回填为案件参与方。
- 不把 `claims`、`guarantors` 等专项表迁移到 `case_party.party_id` 外键。
- 不修改历史 API 日志、会话消息和卷宗原文。

## 3. 权威边界

| 数据 | 权威来源 | 说明 |
| --- | --- | --- |
| 债务人名称和专项画像 | `debtors` | 现有 129 条案件 116 业务记录继续引用 `debtor_id=76` |
| 债务人案件角色 | `case_party` 的 `debtor` 记录 | 必须关联同案 `debtor_id` |
| 资产购买方等非债务人角色 | `case_party` | 不再复用 `debtors`、`contacts` 或自由文本字段 |
| 卷宗中的角色陈述 | `source_*` / 法律文书原文 | 只作为证据，不直接覆盖案件主数据 |

应用层写入债务人时必须同步维护债务人参与方。读取债务人名称时仍以 `debtors` 为准；
`case_party.party_name` 是角色索引和展示字段，不得反向覆盖 `debtors`。

## 4. 表结构

`case_party` 的关键字段：

- `party_id`：参与方记录主键。
- `case_id`：所属案件。
- `debtor_id`：仅 `debtor` 角色可用，精确关联现有债务人；债务人记录删除时级联删除该角色索引。
- `party_name`：参与方名称。
- `party_role`：稳定英文角色编码。
- `is_primary`：同角色下的主要参与方标记。
- `status`：`active` 或 `disabled`，采用软禁用保留审计。
- `source_type`：`case_creation`、`manual`、`migration` 等来源标记。
- `extra_fields`：角色扩展信息，不承载核心名称和角色。
- `created_by/created_at/updated_at`：写入审计字段。

唯一性：

- 同一案件、名称、角色只能有一条记录。
- 一个 `debtor_id` 只能关联一条债务人参与方记录。
- `debtor` 必须有 `debtor_id`，其他角色不得占用 `debtor_id`。

## 5. API 契约

### 5.1 创建案件

`POST /api/ingest/case` 保留必填 `debtor_name`，新增可选
`asset_purchaser_name`。成功后同事务写入：

1. `cases`
2. `debtors`
3. `case_party(debtor)`
4. 可选 `case_party(asset_purchaser)`

### 5.2 参与方管理

- `GET /api/cases/{case_id}/parties`：按案件权限返回有效/禁用参与方。
- `POST /api/cases/{case_id}/parties`：新增或幂等更新非债务人参与方。
- 债务人角色不得通过通用参与方接口创建或改名，必须走债务人专项流程。
- 两个接口复用案件公司、负责人、成员和管理员可见性门禁。

### 5.3 案件画像

`GET /api/case/{case_id}/profile` 新增 `parties` 数组。现有 `debtors` 字段保持
兼容，不改名、不删除。

## 6. 债务人解析规则

上传和摄入按以下顺序解析：

1. `debtor_id` 与案件画像中的债务人精确匹配。
2. 显式 `debtor_name` 与案件债务人名称精确匹配。
3. 案件画像只有一个有效债务人时使用该债务人。
4. 多债务人且未指定 `debtor_id`，或显式名称与主数据冲突时，安全失败并要求确认。

本阶段不再从材料文本生成债务人候选；即使出现“债务人：某主体”，也不得自动创建或
覆盖债务人。删除“受让/转让整体资产即债务人”的规则，不再持久化“未知公司”。

## 7. 数据迁移

2. 从 `debtors` 回填全部确定的 `debtor` 参与方。

4. 不从 `claims.extra_fields`、`legal_documents.extra_fields` 或 OCR 文本推断角色。

## 8. 验收标准

- 案件 116 画像同时返回正确 `debtors` 和两条结构化参与方。
- 使用 `debtor_id=76` 上传时解析为晨光煤矿。
- 传入中信名称作为案件 116 债务人时被识别为冲突，不得写入。
- 多债务人未指定 ID 时不得使用 `LIMIT 1` 或数组第一项。
- “关于受让中国中信金融资产管理股份有限公司整体资产”不得抽取为债务人。
- 上下游 Swagger、README、设计文档和测试同步。

## 9. 回滚与运行要求

- 应用回滚：先回滚 NpaDemo 和 ai_hunter 代码；旧接口不依赖 `case_party`，可继续运行。
- DDL 回滚：仅在确认没有新增参与方业务数据后才允许删除 `case_party`；有数据时先导出，
  不直接删表。
- 案件 116 数据反向回滚只恢复主数据字段；已失效缓存通过重新计算恢复。
- DDL 和应用发布后必须重启 NpaDemo 与 ai_hunter，并执行真实案件画像、参与方和上传冒烟。
