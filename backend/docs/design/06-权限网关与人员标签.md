# 06 · 权限网关 + 人员标签体系（Tier 3-7）

> 状态：**✅ 已实现并合入**。认证信任用户中心 JWT，授权本项目自管（角色→报告段落 audience + 模块级分权），人员标签本地全表。pytest 205 passed。默认 `AUTH_ENABLED=false` 放行，不影响现有接口。

## 1. 架构定位

**用户中心**（独立身份服务，所有智能体共用）= 认证权威：登录、发 JWT、全局账号/角色。
**不良资产** = 信赖方：用户经用户中心登录拿 JWT → 本服务**只验签取身份 + 做授权**，不做登录/发 token。

## 2. 认证层（`auth/identity.py`）

`get_current_identity()` 依赖，取身份三优先级：
1. `Authorization: Bearer <JWT>` —— 配了用户中心密钥/公钥就**验签解码**（claims：`sub`/`name`/`roles`，claim 名 env 可配）。HS256 无依赖手验；RS256 用 PyJWT。
2. 开发态信任头 `X-User-Id` / `X-User-Roles`（`AUTH_DEV_TRUST_HEADERS`）。
3. `AUTH_ENABLED=false` → 返回全权限 admin（现状/测试不受影响）；`true` 且无有效凭证 → 401。

env：`AUTH_ENABLED` / `USER_CENTER_JWT_ALG`(HS256) / `USER_CENTER_JWT_SECRET` / `USER_CENTER_JWT_PUBLIC_KEY` / `AUTH_DEV_TRUST_HEADERS` / `AUTH_JWT_{USER,NAME,ROLES}_CLAIM` / `AUTH_ROLE_PERMISSIONS`。

## 3. 授权层（`auth/permissions.py`）

角色是用户中心全局概念（来自 JWT），但「角色在不良资产能看什么」的**映射归本项目**，**前端/运营可配**：

- 存储：`app_role_permission` 表（role_code → tier + modules + description）。
- 读取三级回退：**DB(`app_role_permission`) → env `AUTH_ROLE_PERMISSIONS` → 代码默认**；进程内缓存，改后清缓存即时生效。
- 配置接口：`GET /roles`（列映射 + 可选模块全集 + tier 选项，供前端权限界面渲染）、`PUT /roles/{role_code}`（建/改，需 admin）。

- **报告段落分权**：audience 层级 `field ⊂ expert ⊂ management`，`visible_audiences(identity)` 取角色最高 tier 及以下。
- **模块级分权**：模块 = report/drilldown/review/progress/corrections/deadline/graph/admin；`require_module(name)` 依赖，无权 403。
- 默认角色映射（业务可调）：项目经理(`project_manager`)=management 全模块+admin；投资专员(`investment_specialist`)=management；法务/财审/尽调/律所律师(`legal_specialist`/`finance_specialist`/`due_diligence_specialist`/`lawyer`)=expert；项目助理/法辅(`project_assistant`/`legal_assistant`)=field。
- 未匹配角色 → 最低可见（field），避免越权。

## 4. 报告段落分权落地（`auth/report_filter.py`）

`filter_report_text(report, visible_audiences)`：按 "### N." 段头切分，只留可见 audience 段（导言/溯源附录保留；复盘段无 audience 恒留）。接线：
- `/chat/invoke` 非流式 final_report、缓存命中 → 过滤；
- SSE：不可见段的 `section_*` 事件不下发、final 过滤；
- `/threads/{id}/messages` 历史 assistant 正文 → 过滤。

`AUTH_ENABLED=false` → identity 为 admin → 可见全部 → 过滤为恒等。

## 5. 人员标签体系（`sql/auth_tables.sql` + `user_service.py` + `routes_users.py`）

标签归不良资产本地（用户中心上线前在本项目维护；上线后改从用户中心同步，表结构不变）。五维：

| 维度 | 存储 | 多选 |
|---|---|---|
| 项目角色 project_role | app_user_tag | ✓ |
| 专业职称 title | app_user_tag | ✓ |
| 专业专长 expertise（分组：通用综合/法律司法/风控侦查） | app_user_tag | ✓ |
| 常住地域 region（省-市-县） | app_user 主表 | 单值 |
| 所属公司名 company | app_user 主表 | 单值 |

`app_tag_catalog` 预置可选项（项目角色 8 / 职称 10 / 专长 19，幂等种子）。
`app_role_permission` 角色→权限映射（8 角色默认种子，前端经 `/roles` 可配）。

接口：
- `GET /me`（仅认证）：身份 + 角色 + 本项目可见 audience/模块 + 标签自省。
- `GET /tag-catalog`（仅认证）：标签预设目录。
- `PUT /users/{id}/tags`、`PUT /users/{id}`、`GET /users/{id}/tags`（require admin）：标签/投影管理。

## 6. 灰度与迁移

- 默认 `AUTH_ENABLED=false`：网关放行，逐步接入；用户中心就绪后设 `true` + 配 JWT 密钥即强制。
- 标签现为本地；用户中心上线后，标签维度可迁移为「从用户中心同步」，`app_user_tag`/`app_user` 作缓存投影，接口契约不变。
- 角色→权限映射始终归不良资产（各智能体自管），不迁移。

## 7. 待联调
- 与用户中心约定 JWT 算法（HS256/RS256）、密钥/公钥分发、claims 字段名（默认 sub/name/roles，可 env 改）。
- 角色码与用户中心对齐（当前用 ROADMAP 项目角色中文名作角色码）。

# v2 设计 · 权限网关重构 + 全量多租户（待实现，2026-06-23 拍板）

> 状态：**规格已定，待实现**。v1（上文）从 JWT 读 roles，与下述边界不符，v2 修正。明天起按 v2.7 阶段推进。

## v2.0 背景与边界（修正版）

- **集成平台 + 用户中心**：未来有集成平台，所有用户注册/登录**唯一入口**走平台用户中心。不良资产是平台下一个产品，后续可独立成产品，但**注册始终经平台用户中心**。
- **私有化部署**：不良资产私有化时需兼容「自带用户中心 + 用户下发的 key」，**无 key 不可用**（license 激活机制，见 v2.4）。
- **边界修正（关键）**：**角色是每个项目自己的**（不良资产的角色 ≠ 其它产品的角色），**不在用户中心**。

| 归属 | 职责 |
|---|---|
| **用户中心（全局）** | 用户身份与属性、认证(发 JWT)、项目准入(能用哪些产品)、**公司归属** |
| **不良资产（本项目）** | 本项目角色定义、用户→角色分配、角色→权限映射、人员标签、**公司内数据隔离** |

一句话：用户中心管"你是谁、属于哪个公司、能进哪些产品"；不良资产管"你在我这儿是什么角色、能看哪些数据"。

## v2.1 认证契约（去掉 JWT.roles）

- JWT claims：`sub`(user_id)、`name`/属性、**`company`(公司 id)**、**`apps`(项目准入清单)**；**不再带 roles**。
- 流程：验签 → 取 user_id + company → （开关）校验 `apps` 含本项目码，否则拒 → 加载**本项目本地角色**(`app_user_role`) → 映射权限。
- **项目准入门（带开关）**：`AUTH_REQUIRE_PROJECT_ACCESS`（默认关，私有化/上线再开）+ `AUTH_PROJECT_CODE`（本项目码）。带 `apps` 且不含本项目码 → 403；没带或开关关 → 跳过。
- **登录即建投影**：首次见到某 JWT 的 user_id → auto-provision `app_user`（这才有"用户列表"来源）。手动加用户**过渡期兼容**，用户中心建好后弃用（用户增删全归用户中心）。

## v2.2 角色来源改本地

- 新增 `app_user_role(user_id, role_code)` 多对多；`/me` 的 roles 改查本地。
- 新增**公司管理员（`company_admin`）角色层级**：限本公司全权（看本公司所有人的案件+历史），区别于跨公司的全局超级管理员 `super_admin`（内部运维）。
- `app_role_permission`（v1 已建）= 本项目角色目录 + 角色→权限映射，前端经 `/roles` 可配。

## v2.3 全量多租户（公司隔离）

### 两层可见性模型
- **第 1 层 · 公司硬墙**：`company_id`（来自 JWT）；A 公司永不可见 B 公司，任何查询先过此墙。
- **第 2 层 · 公司内可见性**：

| 角色 | 公司墙 | 公司内范围 |
|---|---|---|
| 全局超级管理员 `super_admin`（内部运维） | 跨公司 | 全部 |
| 公司管理员 `company_admin` | 限本公司 | 本公司**所有人**的案件 + 历史 |
| 普通成员 | 限本公司 | 仅本人 owner/参与的案件 + 本人会话历史 |

### 隔离锚点（case 级为主 + 两处补标）
- **case 级**：报告/回款/订正/时效/知识图谱都挂 `case_id` → 只要"能看哪些 case"定了，子数据自动跟随。隔离收敛为"我能看哪些 case_id"。
- **thread 级**：`conversation_messages`/thread 按 `thread_id` 存、"看自己历史"按创建人 → thread 盖 `company_id` + `created_by`。
- **全局列表级**（`/threads`、`/users`）：无 case 上下文 → 直接按 `company_id`(+ 成员按 user_id) 过滤。

### 决策（2026-06-23）
- **多人参与 case** → 建 `case_member(case_id, user_id, ...)` 表（成员可见 = 自己创建 ∪ 在 case_member 中）。
- **company 来自用户中心**（JWT `company` claim）；**存量 case 不回填**。
- **RLS 上**（数据库层兜底，非仅应用层）。

### 数据模型改动
- `cases`：+ `company_id`、+ `owner_id`(created_by)。
- 新增 `case_member(id, case_id, user_id, added_by, created_at, UNIQUE(case_id,user_id))`。
- `conversation_messages`（及 thread 元信息）：+ `company_id`、+ `created_by`。
- 其余 per-case 表：通过 case 继承（RLS 用 join 判定，或冗余 `company_id` 列以简化策略）。

### 强制手段（应用层 + RLS 双保险）
- **应用层**：`auth/tenancy.py` —— `visible_case_ids(identity)` / 统一过滤入口；所有 list/get 接入；写入时盖 `company_id`+`created_by`/`owner_id`。
- **Postgres RLS**：租户表加 `company_id` + 启用 RLS 策略；每请求设会话变量 `app.current_company` / `app.current_user` / `app.is_company_admin`；策略示例：
  `company_id = current_setting('app.current_company') AND (current_setting('app.is_company_admin')='1' OR owner_id = current_setting('app.current_user') OR EXISTS(case_member 命中))`。
