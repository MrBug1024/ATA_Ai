# 09 · 审计报告段落权限矩阵与配置化方案

> 状态：初始矩阵已确认，代码与 DDL 已落地，真实库迁移和 seed 同步已按授权完成。本文用于梳理“8 段审计报告按角色精确可见”的权限模型，避免继续依赖代码里写死的 audience 层级。

## 1. 背景

当前审计报告已经拆成 8 段，接口、SSE、历史消息都接入了服务端过滤。但现有过滤维度是 `field / expert / management` 三档 audience：

- `field` 用户只能看 field 段；
- `expert` 用户能看 field + expert 段；
- `management` 用户能看全部段。

这个模型只能表达“层级越高看得越多”，不能表达“财审只看财审相关段、法务只看法务相关段、投资只看投资相关段”的业务矩阵。

因此下一步需要把报告段落权限升级为：

`角色 role_code -> 可见报告段落 section_code`

段落必须有稳定 code 和中文 title，不能只用数字，便于前端配置、权限审计和问题追溯。

## 2. 段落目录建议

## 4. 配置化方案

### 方案 A：继续使用 JSON seed + app_role_permission 扩展 JSON 字段

做法：

- `config/auth_private_seed.json` 中增加 `report_sections` 目录和每个 role 的 `visible_report_sections`。
- 角色权限初始化时写入 `app_role_permission`。
- 如果当前表结构无法承载段落权限，需要给 `app_role_permission` 新增 `visible_report_sections JSONB`。
- 前端角色权限页读取 `/roles`，展示模块权限 + 报告段落权限，保存时写回 DB。

优点：

- 改动小，和现有 `/roles`、seed、权限缓存模型一致。
- 适合当前 v2-A 继续推进。

缺点：

- 段落目录如果也只在 JSON/代码中，前端可配置时仍需要一个稳定目录接口。
- JSONB 字段适合权限集合，不适合复杂审计查询。

### 方案 B：新建段落目录表 + 角色段落授权表

建议表：

- `app_report_section`
  - `section_code`：稳定业务 code，主键。
  - `section_id`：当前 1-8 排序 id，兼容旧报告段头。
  - `title`：段落标题。
  - `audience`：兼容旧模型。
  - `sort_order`：展示顺序。
  - `status`：active/inactive。
  - `description`：段落说明。

- `app_role_report_section`
  - `role_code`：角色 code。
  - `section_code`：段落 code。
  - `created_at / updated_at`：审计辅助。

优点：

- 前端可直接渲染段落目录和角色授权矩阵。
- 权限审计清晰，能查询“某段被哪些角色看到”。
- 不再把业务配置写死在代码中。

缺点：

- 需要新增表和初始化数据。
- 需要迁移现有 `/roles` 接口，增加段落授权读写。

### 方案 C：不新建表，只用 config 文件

做法：

- 所有段落目录和角色矩阵只放 `config/auth_private_seed.json`。
- 服务启动/初始化后读取配置。

优点：

- 最快，不改数据库。

缺点：

- 前端配置后无法持久化，除非再写文件或重跑 seed。
- 多实例部署和权限审计都不理想。
- 不符合“角色做权限审计报告分配的时候可以在前端进行配置”的目标。

## 5. 建议路线

建议采用方案 B。

理由：

1. 你明确要求前端可配置角色的审计报告段落分配。
2. 段落权限属于业务权限，不适合长期留在代码常量里。
3. 后续做权限审计、超级管理员审计、变更记录时，表结构更清晰。
4. `section_code + title + section_id` 能同时满足机器过滤、前端展示和人工追溯。

落地顺序：

1. 新增设计确认：确认第 3 节角色-段落矩阵。
2. 新增 DDL：`app_report_section`、`app_role_report_section`，表和列都补 comment。
3. 更新 seed runner：从 `config/auth_private_seed.json` 初始化段落目录和角色段落授权。
4. 更新权限服务：
   - 新增 `visible_report_sections(identity)`。
   - 多角色取并集。
   - `super_admin`、`company_admin`、`project_manager` 支持 `*`。
   - DB 不可用时回退 seed。
5. 更新过滤逻辑：
   - `filter_report_text` 改为按 `section_code` 或 `section_id` 映射过滤。
   - SSE `_section_visible` 同步使用 section 权限。
   - 历史消息过滤同步使用 section 权限。
6. 更新 `/me` 与 `/roles`：
   - `/me` 返回 `visible_report_sections`。
   - `/roles` 返回段落目录和每个角色的段落授权。
   - `PUT /roles/{role_code}` 支持保存段落授权。
7. 测试：
   - 财审只看到 1/2/5/8。
   - 法务、律师、助理按矩阵过滤。
   - SSE 不下发不可见 section。
   - 历史消息不可见段仍被过滤。

## 6. 暂不做的事

- 不在 prompt 中让模型自行脱敏或按角色重写报告。
- 不把段落权限继续硬编码在 Python 常量中。
- 不只依赖前端隐藏；后端必须过滤。
- 不立即移除 audience。audience 作为兼容和兜底字段保留，直到前端和历史数据完成迁移。
