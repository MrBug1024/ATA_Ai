# 10 · 权限网关 v2-B 案件与会话隔离方案

> 状态：已完成。v2-B.0 共享 DDL、v2-B.1 上游案件租户与成员接口、v2-B.2 下游 tenancy 服务、v2-B.3 会话 metadata、v2-B.4 案件路由接线和 v2-B.5 存量会话迁移均已落地。对象级隔离已进入可运行状态；后续新增普通用户时仍需通过案件 owner / member 管理补齐业务授权。

## 1. 背景

v2-A 已完成：

- 私有化本地用户、公司、角色、登录。
- 本地 `app_user_role` 加载角色，JWT 不写 roles。
- 角色模块权限和审计报告 8 段 `section_code` 权限。

v2-A.1 已完成：

- `/files`、`/chat/upload-files`、`/chat/threads*`、`/chat/invoke` 已接入身份和模块门禁。
- `AUTH_LEGACY_ROLES_ENABLED=false`，私有化生产不再信任 JWT / header roles 回退。

当前仍未完成的是对象级隔离的全路由接线与验收：

- 用户是否能看某个 `case_id`。
- 用户是否能看某个 `thread_id`。
- 公司管理员是否只能看本公司数据。
- 普通用户是否只能看自己 owner 或参与的案件。

## 2. 当前事实

### 2.1 上下游共用真实数据库

已确认：

- `NpaDemo` 是上游工具层 FastAPI 服务，同样由当前项目团队维护。
- `ai_hunter` 是下游 LangGraph 编排服务。
- 两个服务实际共用同一个真实 PostgreSQL 数据库。
- 因此案件归属字段不应只在下游做本地投影；`cases` 应升级为上下游共享的权威数据契约。

### 2.2 当前 `cases` 不满足 v2-B

已重新拉取并阅读上游 `/tmp/NpaDemo_refresh`：

- `v72_fina.sql` 中 `cases` 只有 `case_id`、`case_name`、`case_type`、`status`、`created_at`、`updated_at`、`notes`。
- 上游 `fastapi_server/main.py` 的 `GET /api/cases` 仅按关键词、案件类型、状态分页查询，没有 `company_id` / `owner_id` / 成员过滤。
- 上游目前没有 `case_member` 或租户字段。

结论：v2-B 应采用“共享 DB 契约 + 上下游同步改造”路线，而不是下游单独维护 `case_acl` 作为主方案。

### 2.3 会话与消息

当前会话历史有两套来源：

- `public.checkpoints`：LangGraph checkpointer 表，按 `thread_id` 存状态。
- `public.conversation_messages`：展示友好的消息表，字段包括 `thread_id`、`case_id`、`role`、`content` 等。

当前缺少稳定的 thread metadata 表，导致 `/chat/threads*` 只能按模块拦截，不能判断 thread 属于哪个公司、哪个用户、哪个案件。

`thread_metadata` 仍建议由下游创建在共享库里。原因是 thread 是 LangGraph 会话对象，不是 NpaDemo 的案件主数据，但它必须和共享 `cases` 建立权限关系。

## 3. 推荐路线

推荐 v2-B 采用“共享库权威字段 + 双服务同步接入”的路线：

1. 在共享 `public.cases` 增加租户和 owner 字段，作为案件对象级权限的权威来源。
2. 在共享库新增 `public.case_member`，作为案件成员关系的权威来源。
3. 在共享库新增 `public.thread_metadata`，作为 LangGraph 会话权限入口。
4. 上游 NpaDemo 的案件列表 / 案件详情接口支持按 `company_id`、`user_id`、管理员标记过滤。
5. 下游 ai_hunter 在调用 NpaDemo 前仍先执行 `require_case_access` / `require_thread_access`，形成应用层双保险。

`case_acl` 仅作为备选方案保留，不作为当前主路线：

- 若未来出现无法修改上游 DB schema 的部署场景，可再启用本地投影。
- 当前上下游同库且同团队维护，直接升级共享契约更清晰，也避免同一案件归属存在两套权威来源。

## 4. 共享数据模型草案

### 4.1 调整 `public.cases`

用途：案件主表，同时承担 v2-B 案件租户隔离锚点。

建议新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `company_id` | TEXT | 案件所属公司 / 机构 id；用于公司硬隔离 |
| `owner_id` | TEXT | 案件 owner，默认可理解为案件负责人 |
| `created_by` | TEXT | 案件创建人；可与 owner 不同 |

建议约束：

- 存量数据先回填默认公司 `co_f1824b82e2116701`。
- `company_id` 最终应为 `NOT NULL`。
- `owner_id` / `created_by` 存量无法反推时允许先为空字符串，但普通用户创建新案件时必须写入。
- 后续可对 `company_id` 增加 `REFERENCES app_company(company_id)`，但需要先处理上游建表顺序和存量数据。

新增字段必须补齐 `COMMENT ON COLUMN`，表级 comment 已在上游 DDL 中存在。

### 4.2 新增 `public.case_member`

用途：案件多人参与关系。普通成员可见 owner 案件和参与案件。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL | 主键 |
| `case_id` | BIGINT | 案件 id，关联 `public.cases(case_id)` |
| `company_id` | TEXT | 公司 id，用于硬隔离；必须与 `cases.company_id` 一致 |
| `user_id` | TEXT | 成员 user_id |
| `member_role` | TEXT | 案件内角色，可为空或复用项目角色 |
| `status` | TEXT | active / disabled |
| `added_by` | TEXT | 添加人 user_id |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 最近更新时间 |

建议约束：

- `UNIQUE(case_id, user_id)`。
- `case_id` 关联 `public.cases(case_id)`。
- `company_id` 与 `cases.company_id` 必须一致，由应用层校验；后续可增加触发器兜底。

### 4.3 新增 `public.thread_metadata`

用途：会话权限入口。任何读取 checkpointer / conversation_messages 前，都必须先通过该表判断当前 identity 是否可访问 thread。

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `thread_id` | TEXT | LangGraph thread id，主键 |
| `case_id` | BIGINT | 关联案件 id；没有案件时为 0 或 NULL，需按产品策略处理 |
| `company_id` | TEXT | 会话所属公司 |
| `created_by` | TEXT | 创建人 user_id |
| `last_intent` | TEXT | 最近一次意图 |
| `title` | TEXT | 可选标题缓存 |
| `status` | TEXT | active / deleted |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 最近更新时间 |
| `deleted_at` | TIMESTAMPTZ | 软删除时间 |

建议约束：

- `thread_id` 主键。
- `company_id` 非空。
- `case_id > 0` 时，`case_id` 必须在 `public.cases` 中存在。
- `created_by` 非空，除非是存量迁移或系统任务。

### 4.4 是否给 `conversation_messages` 加列

`conversation_messages` 已有 `case_id`，但建议仍新增 `thread_metadata`，原因：

- thread 是权限入口，不应从多条 message 中反推。
- checkpointer 也只知道 thread_id，必须有单独 metadata 连接权限边界。
- 软删除、列表分页、标题、创建人都更适合放 thread 级表。

后续可以给 `conversation_messages` 补 `company_id` / `created_by` 作为冗余查询加速，但不作为 v2-B 第一优先级。

## 5. 权限规则

统一入口建议放在 `ai_hunter/app/auth/tenancy.py`。

### 5.1 case 可见性

`can_access_case(identity, case_id)`：

- 全局超级管理员：允许。
- 公司管理员：允许访问 `cases.company_id == identity.company_id` 的全部案件。
- 普通用户：允许访问同公司且满足以下任一条件：
  - `cases.owner_id == identity.user_id`
  - `case_member.user_id == identity.user_id AND case_member.status='active'`

拒绝时返回 403，并写安全日志 / 审计事件。

### 5.2 thread 可见性

`can_access_thread(identity, thread_id)`：

- 先查 `thread_metadata`。
- 全局超级管理员：允许。
- 公司管理员：允许访问同公司 thread。
- 普通用户：
  - `thread_metadata.created_by == identity.user_id` 允许；
  - 如果 thread 绑定了 `case_id`，再走 `can_access_case(identity, case_id)`；同案件 owner / active member 可以读取其他成员创建的 thread。

注意：如果 `thread_metadata` 不存在，不能直接读取 checkpointer；应按迁移策略处理。

### 5.3 thread 管理权限

读取和管理分开判断。继续运行、重新生成或删除 thread 仅允许：

- thread 创建人；
- thread 绑定案件的 owner；
- thread 所属公司的公司管理员；
- 全局超级管理员。

普通 `case_member` 可以读取同案件全部 thread，但不能继续运行、重新生成或删除其他成员创建的 thread。新 thread 必须绑定有效 `case_id`；`case_id` 为空仅作为存量迁移兼容状态，不允许普通业务入口新建。
