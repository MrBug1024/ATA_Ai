# AI猎手整体方向与双线建设报告

## 1. 报告目的

本文用于统一说明 AI 猎手当前系统的整体方向、两条业务线现状，以及已完成与待完成事项，作为后续产品拆分、研发排期、前后端联调和对外汇报的基础文档。

同时，本文吸收了后续针对业务落地优先级、材料增量治理和产品排期风险的复盘意见，因此不仅描述理想蓝图，也明确当前阶段哪些事情应该先做，哪些事情应该延后做，避免团队把有限兵力投入到非核心商业价值环节。

---

## 2. 整体方向

### 2.1 总体定位

AI 猎手当前已经不是单一聊天助手，而是一个面向不良资产审计场景的混合编排系统。它的核心目标是把“案件材料摄入、结构化沉淀、图谱追溯、审计生成、追问下钻、任务督办、会话延续”接成一条可复用的产品链。

下一阶段建议正式拆成两条线并行建设：

1. 材料摄入线：面向操作员，只负责上传、OCR、校对、提交、补件。
2. 审计分析线：面向律师、负责人、老板，只负责查看结构化结果、证据追溯、知识图谱、审计报告、督办任务。

这两条线共享同一套底层案件、文件、追溯、图谱与会话基础设施，但在页面、权限、状态机和接口层严格分离。

### 2.2 架构方向

当前推荐并已基本成型的整体架构如下：

1. 接入层：FastAPI 路由
2. 编排层：LangGraph 主图 + 子图
3. 模型层：Router / Report A / Report B / Agent 分角色模型
4. 存储层：PostgreSQL + Redis + MinIO
5. 外部服务层：OCR、案件上下文、任务系统、文书检索、企业画像等

可概括为：

`前端 -> FastAPI -> LangGraph -> Service Adapter -> PostgreSQL / Redis / MinIO / OCR / 外部业务接口`

其中：

- PostgreSQL 负责案件结构化数据、知识图谱、追溯映射、会话检查点等
- Redis 负责 heavy payload 热缓存
- MinIO 负责原始卷宗、页图、衍生工件存储
- LangGraph 负责多步骤流程编排，而不是把所有逻辑揉进单接口

### 2.3 分支方向

系统目前存在两种“分支”概念，需要明确区分。

第一类是业务产品分支：

1. 材料摄入线
2. 审计分析线

第二类是编排执行分支：

1. `ingest_graph`：材料摄入与结构化入库
2. `full_audit_graph`：完整审计报告生成
3. `drilldown_agent_graph`：下钻追问与工具调用
4. `re_audit`：基于修正信息重新审计

当前主图先按业务线与 capability 进行结构化识别，再兼容映射到执行意图：

- 业务线：`operator / audit_analysis / supervision / common`
- 执行意图：`full_audit / drilldown / re_audit / review`
- 低置信度或缺少写操作目标：`clarify`

Phase 1-2 完成“精准分类 + capability 工具约束”；Phase 2.5 在此基础上逐步把执行权迁入业务线子图，同时保留 legacy intent 作为 API、历史 checkpoint 和回滚兼容字段。

Phase 2.5.0 已引入统一注册表和一致性校验；Phase 2.5.1 已完成四个子图骨架和 shadow；Phase 2.5.2 已将七个只读 capability 接入确定性业务线节点；Phase 2.5.3 已接入三个专用图和两个领域 Agent；Phase 2.5.4 已完成 `case.create / material.upload / task.write` 确定性写命令节点、服务端身份注入、会话回绑和任务归属校验，三条写能力的隔离真实 HTTP 和数据库一致性验收已通过。`evidence.resolve` 只回源当前案件卷宗，`caselaw.search` 只检索外部类案。默认和生产仍保持 legacy，尚未切流；下一步是生产部署前检查、`business_line` 灰度切流和观察窗口。详细实施与回滚基线见 [分层意图识别与业务线路由方案](design/12-分层意图识别与业务线路由方案.md)。

后续产品拆分时，前台产品层仍应保持材料摄入与审计分析两个清晰入口；图内四条业务线用于执行职责隔离，两者不是同一层级的划分。

### 2.4 数据追溯方向

AI 猎手后续必须坚持“报告结论可回到原文证据”的原则。当前追溯链路的正确方向已经明确：

1. 原始文件进入 `source_file`
2. 页级数据进入 `source_page`
3. chunk 级证据进入 `source_chunk`
4. 抽取后的实体、关系、断言进入 `kg_entity / kg_relation / kg_claim`
5. 断言与证据通过 `kg_evidence_link` 关联
6. 报告引用通过 `report_citation_map` 建立 `report_ref + citation_id -> claim_id` 映射
7. 前端点击角标后，通过 `/evidence/resolve` 回源到页图、页码、原文片段、高亮框

这是系统可信度的关键，不建议再退回“报告只有结论，没有证据定位”的旧模式。

### 2.5 图谱方向

知识图谱在系统中的定位，不是做展示型概念图，而是做“证据组织与事实关系层”：

1. 实体：企业、人员、资产、矿权、账户等
2. 关系：担保、控制、抵押、执行、诉讼、资金往来等
3. 断言：对关系和风险的结构化表达
4. 证据：支撑断言的原文出处、页图、bbox

图谱的业务价值主要体现在：

1. 报告证据追溯
2. 关系下钻
3. 风险穿透
4. 后续多轮追问时的结构化复用

### 2.6 会话管理方向

系统当前采用“轻消息历史 + 重对象外置”的会话策略，这个方向是对的，应继续保持。

当前会话管理的核心点：

1. `thread_id` 作为会话主键
2. LangGraph Checkpointer 负责持久化会话状态
3. `current_case_id / current_debtor_id / current_debtor_name` 作为长期业务状态
4. `memory_context` 只保留轻量摘要，不把长报告塞进消息历史
5. `heavy payload` 放到 Redis / PostgreSQL，而不是消息数组里

这样做的好处是：

1. 多轮对话不会因为长报告膨胀失控
2. 同案件上下文可以持续复用
3. 报告、全量上下文、图谱快照可以独立回收和恢复

## 3. 两条线的当前情况

### 3.1 材料摄入线现状

#### 3.1.1 已有能力

当前材料摄入线已经具备基础闭环，但还没有完成“批次化、质检化、角色化”。

现有能力包括：

1. 前端已有案件项目管理、案件列表、上传卷宗材料入口
2. 后端已有 `/files/upload-and-ingest` 接口
3. 单次上传文件数已有上限控制，默认最多 5 个文件
4. 原始文件可上传到 MinIO
5. 文本、图片、文档可按类型分流
6. OCR 与文本聚合链路已存在
7. `parse_document` 结构化入库链路已存在
8. 上传后的 `FileItem.url` 已可直接返回域名访问地址

#### 3.1.2 当前不足

当前这条线仍然偏“技术摄入链”，还不是完整的“业务上传模块”。

主要缺口有：

1. 还没有“材料批次”概念
2. 上传后仍然是偏同步处理，没有独立的异步任务状态管理
3. OCR 结果对比链接、人工校对、重新上传判定还没有进入正式产品流程
4. 缺少“确认提交本批次”这一步
5. 缺少“本次新增了哪些类别、仍缺哪些类别”的完整度反馈
6. 缺少“新版本生效、旧版本失效”的材料版本治理
7. 缺少只给操作员使用的角色与权限隔离

#### 3.1.3 结论

材料摄入线已经具备底层能力，但产品形态还处于“直通式上传入库”阶段。下一步重点不是重写 OCR，也不是立刻把上传侧做成完整的文档管理系统，而是补齐最小必要的质检、状态、增量治理和角色边界。

### 3.2 审计分析线现状

#### 3.2.1 已有能力

审计分析线当前已经形成了比材料摄入线更完整的闭环。

现有能力包括：

1. 主图已支持业务线 + capability 分层识别、低置信度澄清和能力级工具约束，并兼容映射到 `full_audit / drilldown / re_audit / review` 执行分支
2. 完整审计报告支持前 4 段、后 4 段分段生成
3. 支持基于用户修正内容走重审，而不是只改文字表面
4. 支持下钻追问与工具调用
5. 支持任务提取与任务创建
6. 支持轻量会话记忆与 LangGraph Checkpointer 持久化
7. 支持案件图谱上下文装载
8. 支持证据追溯、关系证据链、页级高亮锚点
9. 已新增 `report_citation_map`，实现 `report_ref + citation_id -> claim_id` 回源
10. `page_image_ref` 已可返回域名可访问 URL

#### 3.2.2 当前不足

这条线虽然比上传线成熟，但仍有几个关键缺口。

1. 多数 capability 仍折叠到通用 `drilldown_agent_graph`，Phase 2.5 业务线执行子图尚未实施
2. 报告正文前 4 段、后 4 段还没有全面补成正文内联角标
3. 证据追溯已通，但图谱抽取稳定性和键规则还需要继续收口
4. OCR layout 与 bbox 产出能力仍偏基础，复杂版面追溯仍有提升空间
5. 审计模块的角色隔离还没有真正落到后端权限层
6. 缺少“报告生成时绑定材料版本集”的冻结机制
7. 缺少面向老板/负责人视角的更强汇总视图

#### 3.2.3 结论

审计分析线已经具备对外演示和持续迭代基础，但距离“稳定生产形态”还差材料版本冻结、权限治理、正文角标化和上传线正式拆分后的衔接。

从业务成交和客户感知价值来看，审计分析线应优先于材料摄入线的高级产品化。系统最强卖点不是“上传更顺滑”，而是“结论可点击、证据可回源、原文可高亮、关系可穿透”。

## 6. 增量治理原则

### 6.1 为什么要补这一层

系统已经明确支持“追加补充材料审计”，这在业务上是正确的，因为真实案件推进中经常会中途补件。

但如果前端只是多了一个“追加补充”按钮，后端却没有严密的增量治理，那么新旧材料会在图谱、断言和报告层形成冲突，最终把数据库变成一锅互相打架的脏数据。

因此，AI 猎手必须明确以下增量更新铁律。

### 6.2 铁律一：底层原始材料 Append-only

不论是修正版合同、补充清单还是后补扫描件，在 `source_file`、`source_page`、`source_chunk` 层都不做物理覆盖或删除。

规则是：

1. 新材料永远生成新 ID
2. 原材料永久保留
3. 旧材料可以在业务层标记失效、废弃或被替代
4. 原始证据链必须保留，保证审计可信与可追责

### 6.3 铁律二：图谱侧做增量对账，不做无脑全量覆盖

当补充材料进入系统后，`re_audit` 或等价分支不应简单把全部旧 chunk 和新 chunk 混在一起重算覆盖。

更合理的做法是：

1. 给模型提供旧图谱摘要或旧结论台账
2. 给模型提供本次新增 chunk 批次
3. 让模型输出“变更操作指令”，而不是一整份新的全量图谱

最小可行变更指令至少包括：

1. `ADD`：新增实体、关系、断言
2. `OVERRIDE`：新增证据推翻旧结论，要求显式指向被替代的旧结论和新的证据 chunk

### 6.4 铁律三：旧结论软失效，不做硬删除

当新增材料推翻旧结论时，不删除旧 `kg_claim`、旧 `kg_relation`、旧证据链，而是在状态层标记为 `superseded` 或等价状态，并插入新的有效结论。

这样做的结果是：

1. 当前图谱只消费有效结论
2. 历史图谱仍可追溯
3. 报告能解释“为什么原先这么判断，后来为什么变了”
4. 不会因为硬删除而导致旧报告、旧引用、旧证据链瞬间断裂

### 6.5 铁律四：追加补件是快速入口，但不能绕过治理

业务上允许“追加补充材料”的快速入口，不代表可以绕过增量治理。

前端可以轻，后端必须硬。

也就是说：

1. 前端可以不要求操作员每次都创建正式批次
2. 但后端仍要把补件识别为一次独立的增量摄入事件
3. 该事件必须能定位新增了哪些文件、哪些 chunk、触发了哪些结论变更

---

## 7. 建议的阶段推进顺序

### 第一阶段：交付审计高光体验

这一阶段不追求上传侧完美，而是集中火力把“可追溯审计”做成真正能打动业务方的产品体验。

1. 完成正文内联角标
2. 完成点击角标后的证据抽屉或等价高感知回源交互
3. 做出负责人/老板视角的风险总览和关键指标看板
4. 收口实体、关系、断言的稳定键规则
5. 提升 OCR layout 与 bbox 精度，保证回源体验不掉链子

目标是用相对脏、相对不完美的材料，也能生成有证据、有回源、有说服力的报告。

### 第二阶段：建立极简但可靠的材料治理

这一阶段不做复杂人工编辑系统，而是做最小必要治理。

1. 上传异步状态机
2. OCR 结果查看入口
3. 追加补件快速通道
4. Append-only 摄入规则
5. 图谱增量对账与 `superseded` 机制

### 第三阶段：从工具到系统治理

当核心闭环已经产生业务黏性后，再继续补齐治理层。

1. 角色权限 RBAC 正式落表
2. 材料批次化高级管理
3. 缺失材料智能清单
4. 审计与材料版本冻结绑定
5. 更完整的案件运营后台

---

## 8. 当前结论

当前 AI 猎手的基础方向是正确的，尤其是以下几点已经证明值得继续投入：

1. 采用 LangGraph 做主流程编排，而不是继续堆工作流节点
2. 采用 PostgreSQL + Redis + MinIO 的分层存储
3. 采用知识图谱 + 证据回源的可信审计路线
4. 采用轻量记忆 + heavy payload 外置的会话管理方式

同时，下一阶段最重要的不是把上传系统做得像一个完整 DMS，也不是继续无上限堆外围基建，而是优先交付审计高光体验，并为追加补件和图谱增量冲突建立硬约束。

一句话总结：

当前系统已经具备“可用的审计引擎雏形”，下一步要先把“可追溯、可点击、可震撼展示的审计结果”做到极强，再逐步把它建设成“可协作、可追责、可持续运营的双线业务系统”。
