# AI Hunter 追溯与知识图谱 —— 前端调用手册

> 适用读者:前端工程师 / 全栈工程师 / 联调工程师
> 服务入口:`http://10.0.10.2:8081`(可经 CORS 跨域)
> 鉴权:当前未启用,生产部署建议在网关层统一加 Bearer
> 完整 OpenAPI:`GET /openapi.json`,Swagger UI:`GET /docs`,接口目录:`GET /docs-index`

## 0. 读者与目标

本手册覆盖"**从报告角标回到证据页**"和"**知识图谱的可视化与运维**"两条前端核心链路。

学完本手册,你可以:

- 拿到 `/chat/invoke` 的 `final_report` 后,把每个角标 `[1]` / `[2]` 拆到具体证据、页码、bbox
- 渲染"旧结论 → 新结论"演进视图
- 拉一个案件未决的 relation / claim 列表,引导操作员补件
- 渲染实体为中心的多跳关系子图
- 在标杆案件发布前跑一次回源链路卡口校验

**不**覆盖:模型训练 / LLM prompt / 数据库 DDL / 内部架构。这些分别在 `docs/` 下其它文档里。

## 1. 概念总览

### 1.1 端到端数据流

```
┌─────────────┐    ┌──────────────┐    ┌───────────────┐
│  原始卷宗    │ →  │ OCR + 文本    │ →  │ source_page   │
│  (PDF/图片)  │    │ 抽取          │    │ source_chunk  │
└─────────────┘    └──────────────┘    └───────┬───────┘
                                               │  抽取
                                               ▼
                                       ┌───────────────┐
                                       │ kg_entity     │
                                       │ kg_relation   │
                                       │ kg_claim      │
                                       └───────┬───────┘
                                               │  报告
                                               ▼
                                       ┌───────────────┐
                                       │ final_report  │
                                       │ + 角标 [1][2] │
                                       └───────┬───────┘
                                               │  追溯
                                               ▼
                                       ┌───────────────┐
                                       │ 证据抽屉       │
                                       │ + 页图高亮     │
                                       │ + bbox        │
                                       └───────────────┘
```

### 1.2 关键概念(7 个 ID,前端必须分清)

| 概念 | 来源端 | 例子 | 说明 |
|---|---|---|---|
| `case_id` | 业务上下文 | `116` | 案件主键,贯穿所有接口 |
| `file_id` | `source_file.id` | `42` | 单个原始文件,MinIO 一行 |
| `chunk_id` | `source_chunk.chunk_id` | `chunk-1-2-3-4-...` | 文本片段稳定 ID,组合自 `case_id + file_sha256 + page_no + chunk_index + chunk_text_sha256` |
| `claim_id` | `kg_claim.id` | `108` | 一条审计断言(如"晨光煤矿是案件 116 的债务人") |
| `relation_id` | `kg_relation.id` | `77` | 实体间关系(担保 / 出资 / 关联) |
| `entity_id` | `kg_entity.id` | `12` | 实体(公司 / 个人 / 矿权) |
| `report_ref` | `ChatInvokeResponse.final_report_ref` | `final_report:1b8e9b67…` | **不透明**引用串,后端按 `final_report:{uuid}` 生成,**不可自拼、不可从 `thread_id` 派生**,只能从响应/SSE/messages 透传(详见下方 ⚠️) |
| `citation_id` | 报告角标内的字符串 | `1` / `2` / `3` | 报告正文里 `[1]` `[2]` 的数字,前端从渲染好的 markdown 里直接拿 |

⚠️ **常见混淆**:`chunk_id` 是字符串,`file_id` / `claim_id` / `relation_id` / `entity_id` 是 int。

⚠️ **`report_ref` 是不透明字符串,绝不要自己拼**:后端用 `final_report:{随机 uuid}` 生成(例如 `final_report:1b8e9b67fa4d4293ab20aa38273895bd`),与 `thread_id` / `case_id` **无任何派生关系**。前端只能从以下三处之一拿到,然后原样透传给 `/evidence/resolve`、`/graph/demo-case-trace/validate`:

1. `POST /chat/invoke` 响应体的 `final_report_ref`
2. SSE 流式响应 `final` 事件里的 `final_report_ref`
3. `GET /chat/threads/{thread_id}/messages` 里 assistant message 的 `final_report_ref` 字段(刷新页面 / 历史会话用;该字段已在 OpenAPI schema 中稳定返回)

> **刷新历史会话不丢图谱上下文**:`GET /chat/threads/{thread_id}/messages` 的每条 **assistant** message 除 `final_report_ref` 外,还会回放本轮 `/chat/invoke` 当时的图谱关联字段 —— `intent`、`trace_items`、`citation_coverage`、`unresolved_relations`、`unresolved_claims`,结构与 `/chat/invoke` 响应同名字段一致。前端刷新 / 重进历史会话时:
> - **角标 hover tooltip** 直接读 `trace_items`,无需逐条打 `/evidence/resolve`;
> - **覆盖率警告条** 直接读 `citation_coverage`;
> - **「待补件 N」badge** 直接读 `unresolved_relations` / `unresolved_claims`。
>
> 说明:这些字段在该轮落库时快照写入,**仅对修复上线后新生成的会话生效**;更早的历史 assistant 消息这些字段返回空(`[]` / `{}`),前端按空处理即可。`user` 消息恒为空。

> 按 `final_report:{thread_id}` 自己拼会得到一个**无效 ref**。后端仍返回 200,但响应里的 `resolution_status` 字段会标明原因,前端应优先据此判断,**不要把 `evidences:[]` 一律当成"没有数据"**:
>
> - `ok` —— 已解析到证据
> - `no_evidence` —— claim 有效但暂无证据(**合法的空**)
> - `citation_not_found` —— report_ref 有效,但该角标不在这份报告里
> - `ref_not_found` —— report_ref 在库中不存在(**多半是前端自拼了无效 ref**,请改为透传真实 `final_report_ref`)

## 2. 接口速查表(9 个)

| # | 路径 | 方法 | 一句话 | 鉴权 | 响应大小 |
|---|---|---|---|---|---|
| 1 | `/chat/invoke` | POST | 主对话入口,带完整图谱引用 | 必有 `thread_id` | 1~50 KB |
| 2 | `/evidence/resolve` | POST | citation → 证据抽屉 + 页图 | 必有 `case_id` | 2~20 KB |
| 3 | `/files/page-anchors` | GET | 单页 bbox + 页图 | 必有 `file_id` + `page_no` | 1~5 KB |
| 4 | `/graph/relation-evidence` | POST | relation → claim 证据链(分组) | 必有 `case_id` + `relation_id` | 1~20 KB |
| 5 | `/graph/subgraph` | POST | 实体 N 跳子图(可视化) | 必有 `case_id` + `center_entity_id` | 1~100 KB |
| 6 | `/graph/demo-case-trace/validate` | POST | 标杆案件发布前卡口 | 必有 `case_id` + `report_ref` | 1~10 KB |
| 7 | `/files/cases/{case_id}/evolution-items` | GET | 旧 → 新 claim 演进 | 必有 `case_id` | 1~30 KB |
| 8 | `/files/cases/{case_id}/unresolved-items` | GET | 未决 relation / claim(补件治理) | 必有 `case_id` | 0~10 KB |
| 9 | `/files/cases/{case_id}/material-events` | GET | 材料事件时间线 | 必有 `case_id` | 0~30 KB |

所有响应都是 JSON。POST 请求体统一 `application/json`。无文件上传场景,无 multipart。

## 3. 关键场景串联

### 3.1 报告角标联调(最常见)

完整链路 5 步:

```javascript
// 1. 调 /chat/invoke 拿报告
const chatResp = await fetch('/chat/invoke', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({
    thread_id: 'demo-116',
    query: '案件116出具完整审计报告',
    current_case_id: 116,
  }),
}).then(r => r.json());

// 2. 渲染报告正文(角标是 [1][2] 这种字符串)
const reportText = chatResp.final_report;
const reportRef = chatResp.final_report_ref;  // 例如 "final_report:1b8e9b67fa4d4293ab20aa38273895bd"

// 3. 用户点 [1],前端解析出 citation_id="1"
const citationId = '1';

// 4. 调 /evidence/resolve 拿证据抽屉
const evidence = await fetch('/evidence/resolve', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({
    case_id: 116,
    report_ref: reportRef,
    citation_id: citationId,
  }),
}).then(r => r.json());

// 5. 渲染抽屉
const { primary_evidence, primary_page, evidences } = evidence;
drawerList = evidences;                              // 左侧证据列表
firstPage = primary_page.page_image_ref;             // 首屏页图
firstPageAnchors = primary_page.anchors;             // 首屏高亮框

// 6. (可选)用户在抽屉里点另一条证据 → 重新调 /evidence/resolve
//    或者直接调 /files/page-anchors 拿另一页的 bbox
const anotherPage = await fetch(
  `/files/page-anchors?file_id=${primary_evidence.file_id}&page_no=${primary_evidence.page_no + 1}`
).then(r => r.json());
```

```javascript

  .then(r => r.json());

// unresolved.unresolved_relations: 关系没补齐(常见:from_entity / to_entity 在别批次)
// unresolved.unresolved_claims: 断言没补齐(常见:关联 entity 在别批次)
```

### 3.5 实体子图可视化

```javascript
// 用户点图谱上一个实体节点
const subgraph = await fetch('/graph/subgraph', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({
    case_id: 116,
    center_entity_id: 12,                  // 中心实体
    depth: 2,                              // 展开 2 跳
    relation_types: ['guarantee', 'owns'], // 可选,只画担保 / 出资
  }),
}).then(r => r.json());

// subgraph.nodes: 节点列表(每项有 entity_id / label / entity_type / risk_level)
// subgraph.edges: 边列表(每项有 source / target / label / confidence)
//
// 渲染推荐:Cytoscape.js / G6 / D3 force layout 都行
//   - 节点用 entity_type 着色
//   - 边用 confidence 设透明度
//   - 中心节点高亮
```

> **如何拿到 `center_entity_id`**（必须用真实 entity_id，瞎猜会返回空图）：
> 1. 从 `/evidence/resolve` 的 `evidences[].entity_id`、或 `/graph/relation-evidence` 的 `trace_items[].entity_id` 拿——从证据/关系直接跳实体图谱
> 2. 或调 **`GET /graph/cases/{case_id}/entities`** 列出案件全部实体（返回 `entity_id` / `label` / `entity_type` / `degree`，按连接度数 `degree` 降序），让用户在 GraphModal 里选中心点——**推荐入口**
>
> `depth` 现已生效：`1`=一跳邻居，`2`=二跳（最大 2，防止大案件膨胀）。

## 4. 接口详细

### 4.1 `POST /chat/invoke` —— 报告入口

> 完整契约见 `routes_chat.py:108` `ChatRequest` / L165 `ChatInvokeResponse`。这里只列**图谱相关字段**。

**响应体(关键字段)**:

```typescript
{
  thread_id: string,
  current_case_id: number,
  final_report: string,                       // 报告正文,含 [1][2] 角标
  final_report_ref: string,                   // 报告稳定 ID,后续追溯用
  trace_items: [                              // 每条角标的 claim + 证据
    {
      citation_id: string,                    // 报告里的 [1] / [2]
      claim_id: number,
      claim_type: string,
      claim_text: string,
      confidence: number,                     // 0~1
      evidences: [EvidenceItem, ...]          // 见 4.2 节
    }
  ],
  citation_coverage: {                        // 角标覆盖率
    total_claims: number,
    cited_claims: number,
    uncited_claims: number,
    coverage_ratio: number,                   // 0~1
    missing_items: [                          // 没在正文命中的关键 claim
      { citation_id, claim_id, claim_type, claim_text }
    ]
  },
  unresolved_relations: [...],                // 未决关系(本批次)
  unresolved_claims: [...],                   // 未决断言(本批次)
  memory_context: string,                     // 轻量对话记忆
  intent: 'full_audit' | 'drilldown' | 're_audit' | 'review',
  route_decision: {
    route_version: 'v2',
    business_line: 'operator' | 'audit_analysis' | 'supervision' | 'common',
    capability: string,
    confidence: number,
    source: 'rule' | 'model' | 'context' | 'fallback',
    needs_clarification: boolean,
    clarification_question: string
  }
}
```

**前端使用**:
- 渲染 `final_report` 时,**不要自己**把 `[1]` 转成 `<sup>` —— 报告里已经是渲染好的文字,直接展示
- `trace_items` 已经按 `citation_id` 顺序排好,可以拿来做"角标 → 证据预览"工具提示
- `citation_coverage.coverage_ratio < 0.8` 时,建议顶部提示"角标覆盖率低,部分关键结论未挂证据"
- `route_decision.needs_clarification=true` 时直接展示 `final_report` 中的澄清问题，不要自动重试或调用写接口
- Phase 2.5.0 起 `business_line`、`capability`、legacy intent、权限模块和工具范围由后端统一注册表约束；前端只消费 `route_decision`，不要自行维护 capability 到权限/工具的映射
- Phase 2.5.1 已启用后端内部 shadow 对比，但 shadow 不进入 JSON/SSE，也不执行工具；当前执行仍由 legacy `intent` 分支接管，前端无需改调用方式
- Phase 2.5.2 已支持七个只读 capability 灰度进入确定性业务线节点；`evidence.resolve` 只返回本案卷宗证据，`caselaw.search` 只返回外部类案参考且 `case_binding=false/reference_only=true`；切换前后继续保持 `route_decision` 和最终回答字段不变
- Phase 2.5.3 已支持完整审计、修正重审、回款复盘进入专用图，审计下钻和图谱查询进入各自领域 Agent；内部 `business_line_result` 和业务线 context 不进入 JSON/SSE
- `audit.full / audit.reaudit / recovery.review` 必须具备有效案件上下文；缺少时 `needs_clarification=true` 且返回“请先提供要处理的案件编号”，前端只展示该问题，不自动重试
- Phase 2.5.4 已接入 `case.create / material.upload / task.write` 确定性命令节点并通过隔离真实写入验收；生产仍保持 legacy，前端不得自行切换模式，必须等待后端完成部署前检查和灰度发布
- 建案和任务写操作建议传 `write_command`；结构化字段优先于自然语言标签，不得传 `company_id / owner_id / created_by`，这些字段由后端鉴权身份注入

`write_command` 示例：

```json
{
  "thread_id": "case-create-20260720-1",
  "query": "创建案件",
  "write_command": {
    "capability": "case.create",
    "case_name": "某煤矿破产重整案",
    "debtor_name": "某煤矿",
```

### 4.1.1 `POST /chat/invoke?stream=true` —— SSE 流式 + 八段分段事件

报告自 2026-06 起改为**八段专家子 agent 并行生成**。流式时每段的 token 带 `section_id`,前端可**八个分区并行边出边显**,不必等整份报告(约数分钟)生成完。

**开启流式**:请求体加 `"stream": true`(`ChatRequest.stream` 默认已为 `true`),`Accept: text/event-stream`。
```js
const resp = await fetch('/chat/invoke', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Accept': 'text/event-stream' },
  body: JSON.stringify({ thread_id, query, current_case_id, stream: true }),
});
// 用 EventSource 风格解析：每条形如  event: <名字>\n data: <JSON>\n\n
```

**事件序列**（每条 `data` 是一个 JSON 对象）：

| 事件 | 何时 | data 字段 | 前端动作 |
|---|---|---|---|
| `start` | 开始 | `{thread_id, query, current_case_id, uploaded_file_count}` | 初始化会话 |
| `node` | 每个图节点结束 | `{node, summary, payload}` | 可选：进度提示（如"已完成数值引擎"） |
| `section_start` | 某段首个 token | `{section_id, title, audience}` | **建一个分区**（标题=title），按 `audience` 决定可见性渲染（见下） |
| `section_chunk` | 该段正文 token | `{section_id, text}` | **追加**到对应 `section_id` 分区 |
| `section_reasoning_chunk` | 该段思考 token | `{section_id, text}` | 追加到该分区的"思考/折叠"区 |
| `section_done` | 该段生成完 | `{section_id}` | 该分区收尾（去掉 loading） |
| `final` | 全部完成 | 完整 `ChatInvokeResponse`（**与 §4.1 同一份、字段一致**：`final_report`/`final_report_ref`/`trace_items`/`citation_coverage`/`unresolved_*`/`intent`/`memory_context`…；任务不在此响应，由后端落 `create_tasks`） | 用 `final_report` 校准/兜底，存 `final_report_ref` 供追溯 |
| `done` | 收尾 | `{thread_id}` | 关闭连接 |
| `error` | 出错 | `{thread_id, message}` | 报错处理 |

> 八段并行 → `section_chunk` 会**交错**到达（不同 `section_id` 混流），这是正常的，按 `section_id` 路由到各分区即可。`section_id` 取值 `"1"`~`"8"`，对应：1 数据洗脱 / 2 资产清单 / 3 资金流(白手套) / 4 时效看板 / 5 重整盘活 / 6 博弈策略 / 7 督办SOP / 8 增量回款+下钻。
>
> **复盘报告（`intent=review`，见 §4.11）走同一套 SSE 段事件**，但 `section_id` 取值为 `"R1"`/`"R2"`/`"R3"`：R1 对账总览 / R2 差异归因 / R3 经验与规则建议。前端同样按 `section_id` 路由分区即可（与审计 1~8 互不冲突）。

**前端重组（伪码）**：
```js
const sections = {};                 // section_id -> { title, audience, text, reasoning, done }
function onEvent(name, data) {
  switch (name) {
    case 'section_start':
      sections[data.section_id] = { title: data.title, audience: data.audience, text: '', reasoning: '', done: false };
      break;
    case 'section_chunk':            // 交错到达，按 id 追加
      sections[data.section_id].text += data.text; break;
    case 'section_reasoning_chunk':
      sections[data.section_id].reasoning += data.text; break;
    case 'section_done':
      sections[data.section_id].done = true; break;
    case 'final':
      // data 即完整 ChatInvokeResponse：用 final_report 兜底校准，存 final_report_ref / trace_items / citation_coverage
      break;
  }
}
// 渲染：按 section_id 升序排 8 个分区；done=false 显示 loading
```

**`audience` 字段（权限前向兼容）**：`field`（业务/尽调可见）⊂ `expert`（外部专家，不含机密策略）⊂ `management`（仅管理层）。当前默认：1/2/4=field，3/5/8=expert，6/7=management。后端权限网关上线前，前端可先按登录角色对高 `audience` 分区做灰显/隐藏；网关上线后将直接按角色下发可见段。

**兼容**：
- 非段节点（如收尾）的 token 仍走旧的 `text_chunk` / `reasoning_chunk`（无 `section_id`），前端兜底拼到默认区即可。
- 不想做分段 UI 的旧前端：忽略 `section_*` 事件，直接用 `final` 事件里的完整 `final_report` 一次性渲染——**功能不降级**。

### 4.2 `POST /evidence/resolve` —— citation → 证据抽屉

**请求**:
```json
{
  "case_id": 116,
  "report_ref": "final_report:1b8e9b67fa4d4293ab20aa38273895bd",
  "citation_id": "1",
  "claim_id": 0    // 优先用此值；为 0 时才用 report_ref + citation_id 反查
}
```

> **两种入参的 `claim_text` 现已一致**:无论用 `claim_id` 直接反查(图谱「最稳」入口),还是用 `report_ref + citation_id` 反查,响应顶层的 `claim_text`(抽屉标题)都会回填。早期版本 `claim_id` 路径的 `claim_text` 会空,前端从图谱进入证据抽屉时标题退化为 `角标[N]` —— 现已修复。

**响应**:
```typescript
{
  case_id: number,
  report_ref: string,
  citation_id: string,
  claim_id: number,
  claim_text: string,                          // 抽屉标题
  evidences: [EvidenceItem, ...],              // 全部证据(抽屉左侧)
  primary_evidence: EvidenceItem | null,       // 默认聚焦的第一条

    page_no: number,
    page_width: number,                        // 页图宽
    page_height: number,                       // 页图高
    page_image_ref: string,                    // 页图 URL（仅图片类有；PDF 恒空）

    content_type: string,                      // 源文件 MIME；text/* 表示纯文本类，见下方「文本类源文件」
    anchors: [EvidenceItem, ...]               // 首屏高亮框(可能多条)
  }
}
```

**`EvidenceItem` 结构**:
```typescript
{
  chunk_id: string,
  file_id: number,
  file_name: string,
  page_no: number,
  quote_text: string,                          // 原文片段(抽屉正文展示)
  bbox_list: [                                 // 高亮框
    { x: number, y: number, w: number, h: number }
  ],
  page_image_ref: string,                     // 页图 URL（仅图片类有；PDF 恒空）
  source_file_url: string,                    // 原始文件公网 URL（PDF/图片都有，前端据此渲染）
  source_page_id: number,                      // 内部 ID,通常不用
  content_type: string,                       // 源文件 MIME；前端据此切换渲染模式，见下方「文本类源文件」
  entity_id: number                            // 该证据所属 claim 关联的实体 ID，可直接传给 /graph/subgraph
}
```

**前端使用**:
- 抽屉左侧列表 = `evidences`
- 抽屉标题 = `claim_text`
- 首屏渲染 = **`source_file_url`**(所有文件类型都有):图片类直接 `<img src={source_file_url}>`;**PDF 类用 PDF.js 加载 `source_file_url`、按 `page_no` 渲染该页**。⚠️ `page_image_ref` 仅图片类有值、**PDF 恒为空**,不要再依赖它当页图
- 首屏高亮 = 拿到 `page_width` / `page_height`(OCR 页坐标系)后,用 `bbox_list` 的 `x/y/w/h` **按比例**叠加到渲染出的页面上画高亮框(渲染尺寸 ÷ `page_width`/`page_height` 得缩放比)
- 用户在抽屉点另一条 → 再次调 `/evidence/resolve` 或 `/files/page-anchors`

> **文本类源文件(`.txt` 等)的渲染降级 —— 按 `content_type` 判断**
>
> 纯文本类源文件**天然没有页面排版**:入库后 `page_width`/`page_height` = 0、`bbox_list` 恒为 `[]`、`page_image_ref` / 页图为空。这是文件性质决定的,**不是数据缺失,也不是抽取失败**,后端不会为其渲染 PNG 或估算坐标。
>
> 前端按 `content_type` 切换渲染模式,**不要再靠「字段是否为空字符串」去猜「加载中 / 缺失 / 不适用」**:
> - `content_type` 以 `text/` 开头(如 `text/plain`)→ **纯文本模式**:只渲染 `quote_text`,不画页面、不画 bbox。
> - 其它(`application/pdf`、`image/*` 等)→ **页面模式**:用 `source_file_url` + `bbox_list` 走上面的高亮逻辑。
>
> `content_type` 同时出现在 `EvidenceItem`、`primary_page`、`/files/page-anchors` 顶层,取任一即可。

### 4.10 回款闭环 / 进度看板 —— `/cases/{case_id}/progress|recovery|forecast`

项目核心 KPI（拿回多少钱）。一组接口（tags=`progress`，无 `/files`、`/graph` 前缀）：

| 接口 | 方法 | 作用 |
|---|---|---|
| `/cases/{id}/progress` | GET | **看板聚合**：阶段/状态/风险/预期·实际/回收率/预期分档/实收明细/提醒 |
| `/cases/{id}/progress` | PUT | 更新阶段/状态/风险/利润（只传要改的字段） |
| `/cases/{id}/recovery` | POST | 人工录一笔实收（直接计入） |
| `/cases/{id}/recovery` | GET | 实收明细（含待确认） |
| `/cases/{id}/recovery/{rid}/confirm` | POST | 确认一笔自动抽取的待确认收款（确认后才计入） |
| `/cases/{id}/forecast` | POST/GET | 写/读预期回款分档 |

**看板响应**（GET progress）：
```typescript
{
  case_id: number,
  stage: string,            // 资料录入/智能初选/实地尽调/投委会决策/资产确权/执行处置/审计复盘/已归档
  status: string,           // 进行中/暂停/已结案/已归档
  risk_alerts: [{ type, level, source, message }, ...],   // 报告自动聚合(归零/盲估/口径差异/时效) + 人工
  expected_recovery_total: number,   // 预期(元，供计算)
  expected_recovery_total_wan: string,  // 预期(万元/4位/无千分位，供展示，如 "12000.0000")
  actual_recovery_total: number,     // 实收(元，仅计已确认)
  actual_recovery_total_wan: string, // 实收(万元，供展示)
  recovery_ratio_pct: number,        // 回收率%
  profit_distributable: number, profit_distributable_wan: string,
  profit_distributed: number, profit_distributed_wan: string,
  // forecasts[].expected_amount_wan、records[].amount_wan 同为万元展示串
  report_ref: string,                // 预期来源报告
  forecasts: [{ tranche, expected_amount, expected_date, basis, report_ref }, ...],
  records: [{ id, amount, recovered_at, disposal_path, source_desc, operator, status, origin }, ...],
  reminders: [{ type, level, message }, ...],   // 催收 / 利润分配 / 待确认收款
  params: { overdue_days, profit_threshold_pct }
}
```

**关键概念（前端务必处理）**：
- **预期回款**：报告出完后系统自动按 NPV 三档种子化（`basis=报告NPV`）；前端也可 POST `/forecast`（`basis=人工`）补/调。
- **实收两种来源**：① 人工 POST `/recovery` → 直接 `status=confirmed` 计入；② **系统自动抽取**（补卷材料 / 操作员上传卷宗 / 对话里"某房产已回款800万"）→ `status=pending`、`origin=ingest_material|chat`，**不计入实收总额**。
- **待确认流程**：看板 `records` 里 `status=pending` 的需人工核对，调 `POST /recovery/{rid}/confirm` 确认后才计入 `actual_recovery_total`。看板 `reminders` 会有"待确认收款 N 笔"。
- **提醒**：`催收`（已到期预期未收齐）/ `利润分配`（实收达预期阈值）/ `待确认收款`。阈值由后端 env 配置，前端只渲染。

**联调建议流程**：
1. 出报告（`/chat/invoke`）→ 自动种子预期 + 风险 → `GET /cases/{id}/progress` 看预期/风险。
2. 上传含回款的补卷材料 / 或对话说"X已回款" → `GET /cases/{id}/recovery` 看到 `pending` 记录 → 人工 `confirm` → 实收上升、回收率更新。
3. 阶段推进用 `PUT /progress` 改 `stage`。

### 4.11 `POST /cases/{case_id}/review` —— AI 回款复盘对账

项目终结/阶段复盘时，对「预期回款 vs 实际回款」做对账复盘报告。复用八段式段子 agent 框架，产出 3 段：① 对账总览（总量/时点/按处置路径三视角）② 差异归因 ③ 经验与规则建议。**只读对账**：不改 `case_progress`、不抽任务、不种子化预期。

请求（body 可选）：
```typescript

  query?: string }      // 不传用默认"对案件X做回款复盘对账"
```
响应：
```typescript

  case_id: number,
  intent: "review",

  review_metrics: {           // 确定性三视角对账（数值已算好，金额带 *_万元 展示串）
    overall:  { expected_total, actual_total, achievement_rate_pct, variance, expected_total_万元, actual_total_万元, variance_万元, ... },
    timeline: { due_total, not_due_total, timeline_gap, due_achievement_rate_pct, tranches:[{tranche, expected_amount_万元, expected_date, status}], ... },

  }
```

**两种触发方式**（等价）：
- **接口**：`POST /cases/{id}/review`（上方），返回报告全文 + 结构化对账指标（指标可直接喂看板/图表）。
- **对话**：`/chat/invoke` 里 query 带"复盘/对账/回款复盘"等词 → 自动路由到复盘（`intent=review`），SSE 分段流式（段 id `R1`/`R2`/`R3`，见 §4.1.1）。

**持久化与历史**：复盘报告复用报告持久化链路 —— 全文 + `final_report_ref` 落 `conversation_messages`（assistant 行 `intent=review`），刷新会话/拉历史可原样取回，并靠 `intent=review` 与全量审计报告区分。

### 4.12 权威文字订正与追溯 —— `/cases/{case_id}/corrections`

把口头/文字修正（如"水西南路房产估值不对，按 800 万"）升级为**案件级权威订正**：写库、**每次审计自动应用**（跨会话/跨人生效）、全程可追溯。对话里的修正由后端 `extract_correction` 自动写库；本组接口给前端/运营**人工管理 + 追溯**入口。

| 接口 | 方法 | 作用 |
|---|---|---|
| `/cases/{id}/corrections` | GET | 列订正；`?include_history=true` 含 superseded/revoked（追溯审计） |
| `/cases/{id}/corrections` | POST | 人工录一条订正 |
| `/cases/{id}/corrections/{cid}/revoke` | POST | 撤销一条订正（下次审计不再应用） |

订正对象结构：
```typescript
{
  id, case_id, target, instruction, source_query,
  operator_id, operator_name,
  operator_meta,          // 预留：账号体系上线后回填角色/专业标签（多选）
  scope,                  // 生效范围，默认"全案"
  origin,                 // chat（对话抽取）/ manual（人工录入）
  status,                 // active=生效中 / superseded=被同标的新订正覆盖 / revoked=已撤销
  superseded_by,          // 自动覆盖时指向新订正 id
  created_at, updated_at
}
```

**关键概念（前端务必处理）**：
- **自动覆盖**：对同一 `target` 再录订正，旧的自动置 `superseded`（最新权威生效），旧值保留作历史。前端只需展示 `active`，追溯页用 `include_history=true` 看全链。
- **生效面**：订正写库后，该案**任何后续完整审计/重审**都会在加载期自动应用，无需重复输入；不再是"只在当前会话生效"。
- **撤销**：`revoke` 后状态变 `revoked`，下次审计不再应用。

### 4.13 `GET /cases/{case_id}/deadline-board` —— 司法时效看板（红黄绿+倒计时）

审计 `deadline-scan` 引擎产出 → 确定性归一为四级看板。**剩余天数实时计算、红黄绿可刷新**（报告第 4 段是定格叙述，看板用本接口）。阈值由后端 env 配置（红≤30 天 / 黄≤90 天，前端只渲染）。

响应：
```typescript
{
  case_id: number,
  available: boolean,          // 审计引擎不可达时 false（看板空，不报错）
  today: string,               // YYYY-MM-DD
  thresholds: { red_days, yellow_days },
  counts: { expired, red, yellow, safe, unknown, total },
  groups: {                    // 四级 + 未知；组内按剩余天数升序（最紧急在前）
    expired: [{ type, due_date, remaining_days, related_asset, action, level }],
    red: [...], yellow: [...], safe: [...], unknown: [...]   // unknown: 无到期日，remaining_days=null
  }
}
```

**渲染建议**：按 `groups` 四级分区（已过期🔴 / 红🔴 / 黄🟡 / 安全🟢），每项展示 `remaining_days` 倒计时 + `related_asset` + `action`。进度看板 `risk_alerts` 里的"时效已过期/红色预警 N 项"可点击联动跳到本看板。`available=false` 时提示"时效数据暂不可用"。

### 4.14 权限网关 —— 认证(用户中心 JWT) + 授权(`/me`、人员标签)

**认证**:用户经**用户中心**登录拿 JWT,前端调本服务时在 `Authorization: Bearer <JWT>` 带上。本服务只验签取身份(`sub`/`name`/`roles`),不做登录。`AUTH_ENABLED=false`(默认灰度)时无需带 token,全放行。

**授权**(本项目自管):
- **报告段落分权**:按角色可见 audience(field⊂expert⊂management)过滤报告段 —— `/chat/invoke` 返回的 `final_report`、SSE `section_*` 事件、`/threads/{id}/messages` 历史都已**服务端过滤**,前端无需自行裁剪。
- **模块级分权**:无权限的模块接口返回 **403**(progress/review/corrections/deadline/graph/admin)。

| 接口 | 方法 | 作用 |
|---|---|---|
| `/me` | GET | 当前身份 + 角色 + **本项目可见 audience / 可访问模块** + 人员标签(仅需认证) |
| `/tag-catalog` | GET | 人员标签预设目录(项目角色/职称/专长,expertise 带分组) |
| `/users/{id}/tags` | GET/PUT | 查/整维替换用户多选标签(需 admin) |
| `/users/{id}` | PUT | 建/更新用户投影(含 company/region,需 admin) |
| `/roles` | GET | **列角色→权限映射 + 可选模块全集 + tier 选项**(供前端权限配置界面,需 admin) |
| `/roles/{role_code}` | PUT | 配置某角色权限(tier + modules,改后即时生效,需 admin) |

`GET /me` 响应:
```typescript
{
  user_id, username, roles: string[], authenticated: boolean,
  visible_audiences: string[],   // 报告段落可见层级，前端可据此预判
  allowed_modules: string[],     // 可访问模块，前端按此显隐入口
  tags: { project_role: [], title: [], expertise: [], company: "", region: "" }
}
```

**前端建议**:登录后先调 `/me` 拿 `allowed_modules` 决定菜单/入口显隐;报告段落已服务端过滤,直接渲染即可;`AUTH_ENABLED=false` 时 `/me` 返回 admin 全权限。

## 6. 联调 checklist

接入前确认:

- [ ] **CORS 已配**:`CORS_ALLOW_ORIGINS` 包含前端域名(默认是 `*`)
- [ ] **case_id 一致**:所有请求带同一个 `case_id`,别混
- [ ] **thread_id 必填**:`/chat/invoke` 没 `thread_id` 会 422
- [ ] **`report_ref` 用响应里的**:`final_report_ref` 字段,别自己拼
- [ ] **`citation_id` 是字符串**:报告里 `[1]` / `[2]` 是字符串,别当 int
- [ ] **bbox 用相对坐标**:`page_image_ref` 实际像素 = `page_width × page_height`,bbox 的 `x/y/w/h` 是这个坐标系
- [ ] **MinIO URL 公开**:`page_image_ref` / 文件 `url` 直接用,无需 presigned
- [ ] **轮询间隔**:`/files/cases/{case_id}/material-events` 调一次,等 `status=completed` 即可,**别轮询 /chat/invoke**
- [ ] **错误优先看 OpenAPI**:`GET /openapi.json` 比 Swagger UI 准
- [ ] **`upload_batch_id` 格式**:`local-{12位hex}`(前端生成的批次)或后端分配的(从材料事件拿)
- [ ] **批次 ID 不复用给新文件**:同一 `upload_batch_id` 重放只能使用原案件、债务人、材料类别和文件集合；上传新文件必须生成新批次 ID

## 7. 典型错误 + 排查

| 错误码 | 触发场景 | 排查 |
|---|---|---|
| 400 | `current_case_id <= 0` 上传到 `/chat/upload-files` | 上传前先在 `/chat/invoke` 选案件 |
| 400 | `doc_category` 不在白名单(走 `/files/upload-and-ingest` 时) | 从 `case_doc_category_status` 拿合法列表 |
| 409 | `upload_batch_id` 已绑定其他案件/债务人/类别/文件集合 | 为新上传生成新批次 ID，不要改写原批次 |
| 409 | 已完成或非失败批次调用 `/retry` | 只对 `status=failed` 的批次按失败阶段重试 |
| 404 | `upload_batch_id` / `material_event_id` 不存在 | 用 `GET /files/cases/{id}/upload-batches` 拿真 ID |
| 404 | `file_id` 不存在(走 `/files/page-anchors` 时) | 重新走 `/evidence/resolve` 拿最新 evidence |
| 422 | 请求体字段缺/类型错 | 对照 `GET /openapi.json` 的 request schema |
| 500 | `ResponseValidationError` | 报告里 `new_relation_id` 可能是 `None`,前端用 `null` 兼容(已在 v1.1 修复) |
| 500 | 后端 graph enrich 失败 | 看 `journalctl -u ai-hunter-langgraph -n 200` |
| 502/504 | 统一后端业务 API 不可达 | `10.0.10.2:8081` 的 audit / case / task / knowledge / enterprise / doc_category API |

## 8. 跟现有 /chat/invoke 联调的注意事项

`/chat/invoke` 响应里 `trace_items` 已经按 `citation_id` 顺序排好,但**不一定连续**(`[1]` `[3]` `[5]` 这种)。前端渲染时:

1. 报告 markdown 里的角标直接展示
2. 用户点角标 → 用 `citation_id` 查 `trace_items`
3. 角标连续 1-N,但 `trace_items.length` 可能小于 N(有些 claim 没有在正文里出现,但被 LLM 跳过了)
4. 真正点击 → 用 `citation_id` 调 `/evidence/resolve` 拿完整证据

**SSE 流式版本**(`stream=true` 或 `Accept: text/event-stream`):事件类型 `node` 的 `summary` 字段会显示节点进度,如"完整审计已生成,并提取 5 条督办任务"。`final` 事件载荷是 `ChatInvokeResponse`,跟非流式一致。
