# ATA_AI 年审业务线：流程、材料、知识库与达标基线

版本：2026-08-06  
适用范围：`annual_audit` 业务线  
结论性质：项目整改基线，不替代注册会计师对具体项目的专业判断、适用准则判断和签发责任。

## 1. 先给结论

当前项目还不能称为“完整年审已跑通”。现有实现已经能承载年审项目、材料、来源片段、部分确定性分析、图谱、底稿/报告草稿和复核任务，但实际自动化范围仍集中在：

- F1-2 营业收入；
- C5-2 应收账款；
- C1-2 货币资金/银行流水。

这三条线可以作为首个可验收样板，但只是完整年审的一部分。`new_docs/diagrams/business-flow/02-annual-audit.mmd` 定义的业务还包括业务承接、风险评估、重要性、总体策略、具体计划、六大循环、抽样、函证、追加/替代程序、差异汇总、报告、三级复核、正式交付和归档回访。

当前最重要的整改顺序是：

1. 先把材料完整性、来源证据和图谱质量门禁做实；
2. 再把六大循环及完成阶段补齐；
3. 再接入有版本和有效期的法规/准则知识库；
4. 最后才把报告、底稿、复核和签发做成可放行的正式交付链。

## 2. `new_docs` 阅读后的资产盘点

### 2.1 文档实际分布

`new_docs` 当前约有 369 个文件，包含 Word、PDF、Excel、Markdown、Mermaid、JSON 和文本资料。其内容不是单一知识库，而是四种不同性质的资产混合在一起：

| 资产 | 主要内容 | 系统用途 |
|---|---|---|
| 法律法规与政策 | 公司法、会计法、注册会计师法、税法、发票/征管，以及部委公告等 | 只能作为带有效期和来源的权威依据 |
| 会计准则与审计准则 | 企业会计准则、解释、注册会计师审计准则、问题解答、职业道德 | 年审判断、审计程序和报告边界 |
| 审计作业资产 | 六大循环底稿、科目底稿、函证、质量复核、报告和管理建议书模板 | 生成底稿、任务、复核点和交付物 |
| 案例、教材和方案设计 | 标准无保留意见案例、考试教材、业务逻辑、部署方案、Mermaid 流程图 | 训练、样例、术语和产品设计，不能直接当作当前法律依据 |

发现了两个需要立即治理的不一致：

- 旧实现计划按 314 个源文件和“三类库”统计，但当前目录统计包含重复资料、临时锁文件、图纸和方案文档；实际逻辑上应拆为 `law-regulations`、`audit-operations`、`tax-operations`、`cpa-textbooks` 四个集合。
- `new_docs` 中的业务逻辑说明、案例和模板可能是内部经验或历史版本，不能和法律法规放在同一优先级，也不能把文件名中的日期直接当成法律生效日期。

### 2.2 知识库结论：需要，但必须分层

年审必须接入知识库。原因不是让模型“背法规”，而是让每个专业判断能够回答四个问题：依据是哪份文件、哪一条/哪一段、在什么期间有效、与项目证据如何对应。

建议采用以下四个逻辑集合：

| 集合 | 允许回答 | 不允许做的事 |
|---|---|---|
| `law-regulations` | 法律法规、准则、正式公告、解释和生效/废止关系 | 不把旧版本默认为当前版本；不把内部摘要当法律原文 |
| `audit-operations` | 审计准则、问题解答、六大循环程序、函证、报告和复核模板 | 不把模板示例直接变成审计结论；不替 CPA 自动签发 |
| `tax-operations` | 税种法规、征管、申报、税会差异、税务工作底稿 | 不因出现税务异常就自动给出税务意见或申报结论 |
| `cpa-textbooks` | 术语、训练、解释和新员工学习 | 不能作为项目结论的唯一依据，也不能覆盖正式准则 |

AI 注册会计师默认检索 `law-regulations + audit-operations`，遇到税务事项再按权限检索 `tax-operations`；教材只用于解释和训练。`cpa-textbooks` 作为独立集合保留，避免污染正式证据链。

## 3. 年审端到端业务流程

### 阶段 A：业务承接与前期准备

核验客户、审计期间、业务范围、报告目的、独立性、胜任能力、前任会计师沟通、期初余额和资料责任边界，签订业务约定书并建立项目档案。

输出：项目画像、业务约定/保持评价、独立性记录、团队与职责、资料清单、沟通计划、时间表。

放行条件：项目范围、责任边界、审计期间、被审计单位和资料入口已确认。

### 阶段 B：了解、风险评估、重要性与计划

了解行业、治理、业务模式、IT 和内部控制，识别重大错报和舞弊风险，确定重要性和可接受检查风险，编制总体策略、具体计划、抽样计划、函证计划和 AI 自动化边界。

输出：风险评估底稿、舞弊风险底稿、重要性底稿、总体策略、具体计划、控制测试方案、抽样与函证计划。

注意：`new_docs` 图中“8 张表”“函证 ≥70%”“银行函证 100%”只能作为待配置的业务规则候选，不能在代码中硬编码为所有项目的通用结论。规则应有 `ruleset_version`、适用条件、审批人和例外处理。

### 阶段 C：资料摄入、完整性和证据链

材料上传后必须经过文件哈希、版本识别、类别确认、解析/OCR、页码或工作表锚点生成、结构化导入、勾稽校验和缺口清单。原始材料、派生数据、模型摘要和人工结论必须分开保存。

输出：材料目录、重复/错分类提示、解析状态、数据质量报告、缺口清单、来源索引、版本和权限记录。

放行条件：关键结论可回到真实文件、页码、工作表、行列或凭证锚点；缺口不会被系统默认为“无异常”。

### 阶段 D：控制测试和六大循环

完整范围至少包括：

1. 销售与收款：收入确认、截止性、应收账款、账龄、减值、客户集中度、期后回款、函证；
2. 采购与付款：采购真实性、应付账款、付款授权、截止性、未入账负债；
3. 存货：数量/金额、盘点、收发存、计价、跌价准备、寄售/在途和截止性；
4. 薪资与人事：人员、考勤、工资、社保公积金、个税、离职补偿和薪酬计提；
5. 货币资金：银行账户、对账单、余额调节、函证、流水异常、借款和受限资金；
6. 固定资产及长期资产：新增、验收、权属、折旧、减值、在建工程、处置和无形资产。

每个循环都要同时有：控制/风险目标、抽样依据、执行记录、原始证据、异常/例外、替代程序、结论、复核状态和底稿版本。

### 阶段 E：完成阶段、差异和重大事项

汇总审计差异和调整分录，评价未更正错报，检查期后事项、持续经营、关联方、诉讼与或有事项、税务事项、管理层声明，并形成整体审计完成结论。

输出：发现清单、调整台账、未更正错报汇总、重大事项清单、期后事项检查、持续经营评价、关联方清单、管理层声明和完成检查表。

### 阶段 F：报告、三级复核、签发和归档

AI 可以形成报告初稿、底稿草稿、管理建议书草稿和复核任务。项目经理、部门经理、主任会计师/合伙人三级复核应可退回、补证、重新生成并留下版本轨迹。非无保留意见或重大事项必须先完成沟通和专业判断，再决定报告措辞。

只有满足“证据充分、重大事项处理完、复核意见闭环、签字审批完成、成果物哈希和版本已锁定”后，系统才能标记正式报告。其余全部标记为草稿、待补证据、待复核或已退回。

### 4.3 完成和报告材料

关联方及关联交易清单、董事会/股东会/管理层会议纪要、律师函或诉讼资料、期后事项清单、持续经营预测、管理层声明、审计调整和未更正错报确认、重大事项沟通记录、正式报告模板、财务报表及附注模板、管理建议书、底稿目录和三级复核表。

### 4.4 当前实现和目标的差距

当前 `document_repository.py` 的标准结构化表主要覆盖：`trial_balance`、`journal_entries`、`receivables`、`bank_statements`；当前分析服务主要覆盖 `sales_receivables` 和 `cash_and_bank`。这意味着上传入口不能只检查“有文件”，还必须检查：

- 文件是否属于正确项目、期间和版本；
- 是否覆盖需要执行的循环和报表科目；
- 是否能解析出可计算的数据行；
- 总账、明细账、报表和派生底稿是否勾稽；
- 关键异常是否有原始证据和替代程序；
- 尚未覆盖的循环是否明确标记为“未执行”，而非“无异常”。

## 5. 最终产出与“达标”定义

完整年审的成果不是一份 Markdown 或一段模型回答，而是可交付、可复核、可归档的成果包：

1. 项目与计划包：业务约定/保持评价、独立性、风险评估、重要性、总体策略、具体计划；
2. 资料与证据包：原始材料、解析版本、数据质量、缺口、文件/页码/表格行列/凭证锚点；
3. 工作底稿包：六大循环、科目底稿、控制测试、实质性程序、抽样、函证和替代程序；
4. 审计结论包：发现、调整、未更正错报、重大事项、期后事项、持续经营、关联方、税务/法律事项、管理层声明；
5. 复核与正式交付包：三级复核及整改、正式审计报告、附送财务报表及附注、管理建议书、沟通文件、签字审批、归档和回访。

最小验收标准：

- 任何报告结论都能回溯到项目内真实证据，并显示证据版本和知识/规则版本；
- 任何工作底稿都能说明程序、样本、证据、异常、结论和复核状态；
- 缺失资料、未执行程序、低置信度 OCR、冲突关系、未决实体和未解决复核意见都会阻断正式签发；
- 图谱只显示当前有效、端点已解析且有证据支持的关系；未决项有原因、来源和人工处理入口；
- 报告、底稿、财务报表/附注、管理建议书和复核日志均有版本、哈希、权限和归档记录；
- 至少用一套真实或脱敏案例完成“上传→解析→勾稽→六大循环→发现→底稿→报告初稿→三级复核→正式交付”的负面和正面回归。

## 6. 图谱问题的根因与本次修复

### 6.1 根因

1. 抽取提示词把业务角色直接当成实体类型，后端、数据库和前端没有同一套 taxonomy；
2. 缺省类型会落成 `unknown`，前端因此显示“未分类”；
3. 无模型或结构化输出失败时，回退逻辑人为生成“被审计单位关联自身”的占位自环；前端为避免画布污染又删除自环，最终表现为没有有效关系；
4. 关系端点缺失时仍生成包含空端点的稳定 key，后续只能以难以重放的未决关系存在；
5. 子图 SQL 没有过滤 `invalid/superseded` 关系和失效实体，历史错误关系仍可能进入画布；
6. 关系抽取、实体落库、断言证据和图谱展示之间没有统一的质量门禁，导致“有节点但没有可核验边”或“有边但没有证据”。

### 6.2 已实施的安全修复

- 新增统一的实体/关系类型标准化：`audited_entity→company`、`bank_account→account`、`customer/supplier/related_party→organization`、`unknown→other` 等；
- 更新年审图谱提示词，要求角色进入 `attributes.role`，不再把角色名称当成新类型；
- 回退模式只保留有证据的被审计单位锚点，不再生成占位自环；
- 缺少关系端点时不生成空端点 hash，保留 `missing_entity_reference` 和缺失端点，交给未决队列处理；
- 子图只读取 active 关系和 active 实体，并按置信度和 id 稳定排序；
- 前端补齐账户、发票、凭证、交易、会计科目及历史别名的显示映射，真正空类型才显示“未分类”。

这解决的是图谱链路的结构性问题，不等于模型已经完成高质量关系抽取。下一步仍要做有标注样本的离线评测：实体准确率、关系准确率、端点解析率、证据覆盖率、未决率、重复合并率和人工接受率。

## 7. 知识库预设计

### 7.1 文档元数据

至少保留：

```text
document_id, title, library_slug, category, doc_type, tax_type,
subject_code, issuing_body, issue_date, effective_date, expiry_date,
version, source_family_id, supersedes_document_id, authority_level,
file_path, file_sha256, parser_version, ingest_status, review_status,
access_scope, ingest_job_id
```

切片还要保留 `document_id、page_no、paragraph_no、article_no、sheet_name、row_range、anchor_text、chunk_hash、embedding_model、index_version`。法律和准则以条/款为优先边界；底稿和模板按章节、程序、字段说明切分；建议在离线评测后确定 200–500 token 的法律切片和更长的表格/程序切片，不要把一种长度硬套所有文档。

### 7.2 入库流程

扫描 → SHA-256 去重 → 文件类型和来源分类 → 解析/OCR → 结构化元数据 → 业务专家审核 → 按结构切片 → 嵌入/关键词索引 → 混合召回与重排 → 检索评测 → 发布索引版本。

默认采用人工或批量发布；实时联网查询只能作为授权、隔离的补充，不能绕过本地版本、权限和审计日志。

### 7.3 冲突和有效期

同一 `source_family_id` 下按发布机关、文件版本、生效日期、废止日期和适用地域排序。默认返回当前有效版本，同时在存在冲突时保留旧版本和冲突提示；不能只按上传时间覆盖。地方税务政策、行业监管要求、客户内部制度应单独标明适用地域/客户，不能混入全国通用规则。

`new_docs` 中的土地增值税清算、地方税务政策和内部业务逻辑应在知识库中作为待补证据/业务指导，不得在没有当地政策和生效信息时自动形成税务结论。

## 8. 分阶段整改路线

### P0：可信数据和图谱闭环

- 完成材料分类、版本、项目/期间校验和结构化完整性门禁；
- 补充图谱端点解析、证据覆盖、冲突、未决项和重建版本；
- 为图谱抽取建立 50–100 条人工标注的年审样本，跑出可比较指标；
- 将当前只覆盖收入/应收/货币资金的状态在 UI 和报告中明确标为“部分范围”。

### P1：六大循环和完成阶段
